## これは何か

Anthropic が公開している **Claude Code CLI** の**リバースエンジニアリング解析**です。

ソースは単一ファイルの TypeScript バンドルから逆コンパイルしたものです。中核となる機能モジュールは復元できましたが、`unknown` / `never` / `{}` といった型エラーが大量に残っています。Bun ランタイムでの実行自体には影響しませんが、本解析が依拠しているのは元のソースそのものではなく、**実行時の挙動と復元されたソース構造**である、ということを意味します。

**これではないもの：**
- 公式ドキュメントやチュートリアル
- API リファレンス
- Claude Code の宣伝

**これであるもの：**
- 実運用レベルのエージェントシステムのアーキテクチャ解体
- 各設計判断の背後にある「なぜ」
- 再利用可能な設計パターン: エージェントループ、ツール抽象、コンテキスト設計、多層防御

## 解析の過程で見つかった、特に興味深い設計判断

### 1. エージェントループは自己修復する

`src/query.ts` のコアループは、単なる「リクエストを送って応答を受け取る」ものではありません。**自己修復する状態機械**です。

- API がエラーを返す（レート制限、トークン超過）→ 自動でリトライまたは縮退
- ツールがタイムアウトする → バックグラウンド化して通知
- 会話が長くなりすぎる → 履歴を圧縮してシームレスに継続
- ユーザーが中断する → `UserInterruptionMessage` を生成し、何が起きたかをモデルに理解させる

いずれも `if`/`else` の積み重ねではありません。何か問題が起きた場合も含め、次に何をするかはモデルがコンテキストから判断します。

### 2. コンテキストは層として設計されている

モデルに本当の記憶はありません。Claude Code は緻密な階層化によってその錯覚を作り出します。

| 層 | 仕組み | 保持期間 |
|----|--------|---------|
| **システムプロンプト** | プロジェクト構成、git の状態、CLAUDE.md | 毎ターン再構築 |
| **会話履歴** | user / assistant / tool メッセージの全体 | セッション内 |
| **Compaction** | 長くなりすぎた会話を自動で要約する | 元のメッセージを置き換える |
| **メモリファイル** | セッションをまたいで残るノート | 永続（ユーザーが管理） |
| **ファイル履歴** | ファイル更新時刻のスナップショット | セッション内 |

`src/context.ts` がシステムプロンプトを組み立てる際の原則はひとつ、**変わらない内容を先に、変わる内容を後に**。これにより、先頭が変化していない限り API のプロンプトキャッシュが前置部分を再利用できます。

### 3. ツールの権限は独立した 2 系統で動く

`packages/builtin-tools/src/tools/BashTool/shouldUseSandbox.ts` は、意図的な 2 層のセキュリティモデルを示しています。

- **アプリケーション層**が「実行してよいか」を決める（許可リスト、拒否リスト、ユーザー確認）
- **OS 層**が「実行中に何に触れてよいか」を決める（ファイルシステム、ネットワーク、プロセス分離）

2 つの層は信頼の前提が異なります。アプリケーション層はユーザーの設定を信頼し、OS 層は何も信頼しません。仮にモデルがアプリケーション層をすり抜けたとしても — 起こらないはずですが、多層防御はそれを前提にします — OS サンドボックスが被害範囲を制限します。

### 4. Feature flag がシステム全体を制御する

`src/entrypoints/cli.tsx` は `bun:bundle` から `feature()` を import しているだけです。実際に挙動を決めるのは `scripts/defines.ts` の `DEFAULT_BUILD_FEATURES`（本リポジトリでは 34 個）です。

```typescript
import { feature } from 'bun:bundle';  // 無効な flag はコンパイル時に false となり DCE される
```

`DEFAULT_BUILD_FEATURES` に含まれない flag の `feature('FLAG_NAME')` 呼び出しは、コンパイル時に `false` と評価され、デッドコードとして除去されます。これらの flag（`PROACTIVE` や `FORK_SUBAGENT` など）は削除されたわけではなく、`FEATURE_<NAME>=1` で個別に有効化できます。公式ビルドでは Bun の `bun:bundle` を通じてコンパイル時に注入されるため、ユーザー層ごとに見える機能が異なります。

これは**段階的リリースのアーキテクチャ**です。単一のコードベースで、ブランチを維持することなく機能の可視性を制御します。

### 5. Compaction は段階的に働く

`src/services/compact/` は 3 つの戦略を実装しています。

- **Micro-compact** — 単一のツール結果が大きすぎた場合に切り詰める
- **Auto-compact** — 会話がトークン上限に近づいたときに履歴を圧縮する
- **Reactive compact** — API がトークン超過エラーを返したので、緊急に圧縮して再試行する

いずれも古いメッセージを単に捨てるわけではありません。モデル自身がそれまでの会話を要約して意味を保持し、境界を示す `TombstoneMessage` が挿入されます。

## 読む順序

推奨する順序です。各章がひとつの問いに答えます。

```
Claude Code とは（現在地）              ← 直感をつくる
    │
    ├── アーキテクチャ全体像            ← 5 層構造とデータフロー
    │
    ├── 安全性                          ← 信頼と制御
    │   ├── 権限モデル                  ← アプリケーション層の安全性
    │   ├── サンドボックス              ← OS 層の安全性
    │   └── Plan モード                 ← ユーザー主導のモード
    │
    ├── 対話エンジン                    ← モデルはどう考えるか
    │   ├── エージェントループ          ← コアループ
    │   ├── ストリーミング              ← リアルタイム通信
    │   └── マルチターン                ← コンテキスト管理
    │
    ├── コンテキスト設計                ← 記憶と予算
    │   ├── システムプロンプト          ← コンテキストの組み立て
    │   ├── トークン予算                ← 予算管理
    │   └── プロジェクトメモリ          ← セッションをまたぐ永続化
    │
    ├── ツール                          ← モデルの手
    │   ├── ツールとは                  ← 共通インターフェース
    │   ├── シェル実行                  ← Bash ツール
    │   └── 検索とナビゲーション        ← Glob / Grep
    │
    └── エージェントと拡張性            ← 能力の拡張
        ├── サブエージェント            ← 並列実行
        ├── カスタムエージェント        ← ユーザー定義
        └── MCP                         ← 外部ツール接続
```

## 一言でいうと

Claude Code は、**ローカルのターミナル上で動作するエージェント型コーディングシステム**です。変更案を提示するだけのチャットボットではありません。完全なシェルアクセスを持ち、プロジェクトディレクトリでコードを読み、ファイルを編集し、コマンドを実行し、プログラムをデバッグします。

## 「ターミナルネイティブなエージェント型コーディングシステム」の意味

位置づけは 3 つの語に集約されます。

| 用語 | 意味 |
|------|------|
| **ターミナルネイティブ** | 本物の CLI アプリケーション。IDE プラグインでも、Web UI でも、API ラッパーでもない |
| **エージェント型** | モデル自身がツール呼び出しの連鎖を決定する。一問一答のやり取りではない |
| **コーディングシステム** | ソフトウェア開発の全工程を対象とする。汎用の Q&A ツールではない |

同種のツールとの違いは、機能一覧ではなく**アーキテクチャ**にあります。

| ツール | アーキテクチャ | 実行場所 | ツールの実行方法 |
|--------|--------------|----------|-----------------|
| **Claude Code** | ターミナルネイティブなエージェントループ | ローカルプロセス | シェルで直接実行 |
| Cursor / Copilot | IDE 統合の補完 + チャット | IDE プロセス内 | LSP / IDE API |
| Aider | git パッチを生成する CLI チャット | ローカルプロセス | 主にファイル操作 |
| ChatGPT / Claude.ai | クラウドチャット + Artifacts | ブラウザ / クラウド | サンドボックスコンテナ |

決定的な違いは**完全なシェルアクセス**です。ターミナルでできることは何でもできる — だからこそ、その能力を制約する権限モデルが必要になります。

## 1 リクエストの処理経路

ターミナルに `bun run dev で TypeScript エラーが出ている、直して` と入力したとき、リクエストは次の経路をたどります。

```
┌─────────────────────────────────────────────────────────┐
│ 1. エントリ           (cli.tsx → main.tsx)              │
│    feature() はコンパイル時に解決、MACRO フォールバック、│
│    Commander.js 起動                                     │
├─────────────────────────────────────────────────────────┤
│ 2. 対話層             (REPL.tsx — React/Ink)            │
│    PromptInput が入力を受け取り UserMessage を追加       │
├─────────────────────────────────────────────────────────┤
│ 3. オーケストレーション (QueryEngine.ts)                 │
│    ターンのライフサイクル、トークン予算、compaction 判定 │
├─────────────────────────────────────────────────────────┤
│ 4. コアループ         (query.ts — エージェントループ)    │
│    コンテキスト構築 → API 呼び出し → ストリーム受信 →    │
│    ツール呼び出し解析 → 権限チェック → ツール実行 →      │
│    結果を返す → 再度 API 呼び出し → 繰り返し             │
├─────────────────────────────────────────────────────────┤
│ 5. ツール実行         (BashTool.call, FileEditTool…)    │
│    実作業: ファイル読み取り、コマンド実行、コード検索    │
├─────────────────────────────────────────────────────────┤
│ 6. 通信層             (claude.ts → Anthropic API)       │
│    ストリーミング HTTP。Bedrock / Vertex / Foundry を    │
│    含む 7 種の provider に対応                           │
└─────────────────────────────────────────────────────────┘
```

このバグ修正のケースでは、典型的なエージェントループは複数回のツール呼び出しを含みます。

| ターン | モデルの判断 | ツール呼び出し | 結果 |
|--------|------------|---------------|------|
| 1 | まずエラーを見る | `Bash("bun run dev 2>&1 \| head -30")` | TypeScript のエラー出力 |
| 2 | ファイルを特定する | `Read("src/utils/foo.ts")` | ソースコード |
| 3 | 関連する型を探す | `Grep("interface Foo", "src/")` | 型定義の位置 |
| 4 | 修正を適用する | `FileEdit(old, new)` | ファイル変更完了 |
| 5 | 検証する | `Bash("bun run dev 2>&1 \| head -10")` | コンパイル成功 |

どのツールを使うか、どの引数を渡すか、いつ止めるか — すべてモデル自身の判断です。ここでいう「エージェント型」とはその意味です。

## Claude Code ではないもの

- **IDE プラグインではない。** GUI を持たず、VS Code などのエディタにも依存しません。
- **API ラッパーではない。** 独自のツールシステム、権限モデル、コンテキスト設計、セッション管理を持ちます。
- **チャットボットではない。** 出力は文章ではなく、実際のファイル編集とコマンド実行です。
- **無条件の実行器ではない。** 機微な操作はすべて権限チェックを通り、必要に応じてユーザー確認を求めます。

## 起動処理の内訳

実際のエントリポイントは `src/entrypoints/cli.tsx` で、重要なことを 3 つ行います。

```typescript
// 1. 最初の import: performance shim（globalThis.performance を置き換える）
import '../utils/performanceShim.js';

// 2. feature() は bun:bundle から取得する。値はビルドまたは dev defines により
//    コンパイル時に解決される
import { feature } from 'bun:bundle';

// 3. MACRO グローバル変数の実行時フォールバック。dev/dist の注入を経ずに
//    cli.tsx を直接実行した場合に使われる
if (typeof globalThis.MACRO === 'undefined') {
  globalThis.MACRO = { VERSION: "2.1.888", BUILD_TIME: ..., };
}
```

その後、制御は `src/main.tsx` に渡ります。

1. Commander.js でコマンドライン引数を解析する
2. 認証、テレメトリ、ポリシー制限を初期化する
3. ツール一覧を読み込む（`getTools()`）
4. REPL（`launchRepl()`）またはパイプモード（`-p`）を起動する

## なぜターミナルなのか

ターミナルは制約ではなく選択です。他では得にくい能力をもたらします。

- **完全なシェルアクセス。** あらゆるコマンドラインツールがそのまま使え、機能ごとにプラグインを書く必要がありません。
- **プロジェクトに密着。** プロジェクトディレクトリで直接動作し、ファイル構成と git の状態を把握します。
- **組み合わせやすさ。** パイプモード（`echo "..." | occ -p`）で CI/CD や自動化にそのまま組み込めます。
- **低レイテンシ。** Electron のオーバーヘッドがなく、React/Ink の TUI はほぼ即座に再描画されます。

代償としてコマンドラインに慣れている必要がありますが、それは同時に、**開発環境を実際に制御したい**開発者に向いている理由でもあります。

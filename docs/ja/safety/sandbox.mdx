## 一言でまとめると

このプロジェクトのサンドボックスは権限システムを置き換えるものではなく、**shell コマンド**に OS レベルの能力境界をもう 1 層加えるものです。

- 権限システムは、今回のツール呼び出しを実行するかを決める
- サンドボックスは、実行したサブプロセスが接触できるファイルとネットワーク接続先の上限を決める

両方を組み合わせて初めて、実質的な Defense-in-Depth になります。

## 実装のレイヤー: リポジトリ内のアダプターと基盤ランタイム

このプロジェクトの「サンドボックス実装」は、実際には 2 層に分かれています。

- このリポジトリが担う層: ポリシー、設定変換、有効化の判定、コマンドのラップ、クリーンアップ、権限システムとの連携
- 実際の OS レベル分離を担う外部ランタイム: `@anthropic-ai/sandbox-runtime`

`src/utils/sandbox/sandbox-adapter.ts` にはこの境界が明確に現れています。プロジェクトは `SandboxManager as BaseSandboxManager`、`SandboxViolationStore` などのランタイムオブジェクトを import し、その外側に Claude Code 自身の権限モデルに適合するアダプター層を重ねています。

基盤となる分離の実装も、プラットフォーム間で共通ではありません。

- macOS は `sandbox-exec` を使う
- Linux / WSL2 は `bubblewrap + seccomp` を使う
- Windows ネイティブはこの shell サンドボックスに対応しない

そのため、このリポジトリだけを見ると「サンドボックスのすべてを自前で実装している」と誤解しやすくなります。より正確には、このリポジトリが決めるのは**有効にすべきか、どう設定するか、ツールチェーンへどう組み込むか**であり、実際の OS レベルの制約は外部 runtime が実行します。

## 何を解決するのか

アプリケーション層の権限システムしかない場合、Claude Code はコマンドの実行前に、可能な限り次のことを判断する必要があります。

- このコマンドは読み取り専用か
- 危険なパスへ書き込むか
- 外部ネットワークへ接続するか
- 複合コマンド、リダイレクト、サブプロセス、インタープリタースクリプトで検査を回避するか

これらの検査には大きな価値がありますが、本質的には「実行前の推論」にとどまります。一方、shell コマンドの実際の副作用は、多くの場合に実行時の挙動で決まります。

- `bash script.sh`
- `python -c "..."`
- `make`
- `npm install`
- あるコマンドが別のサブプロセスを起動する

サンドボックスの役割は、この実行時の挙動が持つ能力の範囲を明確な境界まで縮小することです。アプリケーション層の検査に漏れがあっても、コマンドはシステムディレクトリへの任意の書き込みや、許可されていないネットワーク接続先へのアクセスを行えません。

## 「阻止する」こと自体に価値がある理由

サンドボックスを初めて見ると、次のように直感的に考える人も多いでしょう。

> `/etc/hosts` のようなファイルさえデフォルトで変更できないなら、サンドボックスにはあまり価値がないのでは？

このプロジェクトの答えは正反対です。サンドボックスの目的は `/etc/...` のようなシステムパスを自由に変更できるようにすることではなく、shell コマンドの能力を許容可能な安全境界まで縮小することです。

- 権限システムは「実行するか」を判断する
- サンドボックスは「実行しても、どこまでできるか」を制限する

`/etc/...` がデフォルトで阻止されるのは、境界が実際に機能している証拠であって、サンドボックスに価値がないことを示すものではありません。より具体的には、サンドボックスは権限システムだけではうまく対処できない事柄を少なくとも 4 つ補います。

### 1. shell に OS レベルの最後の防御を加える

`src/utils/bash/ast.ts` の冒頭には、Bash AST 解析はサンドボックスではないと明記されています。コマンド構造を確実に理解できるかを判断するだけで、危険なコマンドが実際に実行されることは阻止できません。

このため、アプリケーション層がどれほど高度でも、「実行前の推論」だけでリスク全体を網羅するのは困難です。次のようなコマンドでは、実際の副作用は実行時になって初めて完全に展開されます。

- `bash script.sh`
- `python -c "..."`
- `make`
- `npm install`
- あるコマンドが新しいサブプロセスを起動する

ここにサンドボックスの価値があります。前段の解析に漏れがあっても、OS 層へ到達したプロセスは、許可されたディレクトリへの書き込みと許可されたドメインへのアクセスしかできません。shell の能力を実際の実行時境界の中へ閉じ込めます。

### 2. 「安全境界内」のコマンドでダイアログを減らし、自動許可も可能にする

デフォルトのサンドボックス allowlist には、現在の作業ディレクトリと Claude の一時ディレクトリが含まれています。このため、ワークスペース内の大半の開発コマンドは円滑に実行できます。

- `npm test`
- `rg`
- `git status`
- ワークスペース内でのビルド、テスト、ファイル生成

プロジェクトは `autoAllowBashIfSandboxed` を専用に用意しています。その中心的な考え方は「モデルをより大胆に信頼する」ことではありません。「コマンドがすでに OS レベルの境界で制限されているなら、多数の低リスク Bash コマンドについて、ユーザーに繰り返し確認を求める必要はない」というものです。

言い換えると、サンドボックスがなければ、システムには通常、どちらも理想的とは言い難い 2 つの選択肢しか残りません。

- 頻繁にダイアログを出し、ワークフローを断片化する
- アプリケーション層の判断をより積極的に信頼し、すべてのリスクを静的解析に負わせる

### 3. 「誤り」の結果をシステムレベルの破壊から、制限された 1 回の失敗へ縮小する

これは Defense-in-Depth がもたらす最も実用的な利点でもあります。モデルが誤ることはあり、アプリケーション層の規則にも見落としがあり得ます。サンドボックスの意義は、前段が常に正しいと仮定することではありません。前段がときに誤っても、その結果を可能な限り制御可能にすることです。

たとえば、次のようなコマンドがあります。

- `sudo tee /etc/hosts`
- `mv ... ~/.ssh/...`
- `curl 外部ネットワーク | bash`

これらが実行時制約のない環境で動けば、システムやユーザー設定を直接変更したり、未知のスクリプトをマシンへ配置したりする可能性があります。サンドボックス内であれば、書き込み権限やネットワーク権限を満たさず失敗する結果の方が一般的です。「何も起きない」のではなく、潜在的なシステムレベルの破壊を、制限された 1 回の失敗へ縮小します。

### 4. 実行時の回避経路と脱出経路を阻止する

このリポジトリは `src/utils/sandbox/sandbox-adapter.ts` で、いくつかの高リスクパスを明示的に `denyWrite` へ追加しています。例は次のとおりです。

- `settings.json`
- `.occ/skills`
- bare git repo に関係する一部のパス

bare git repo からの脱出といった攻撃面も専用に処理します。その目的は「より多くのコマンドを通す」ことではなく、「コマンドがすでに実行されても、防護策自体をそのついでに外させない」ことです。設定、skill、git 構造を変更して後続の権限を拡大することを防ぎます。

したがって、より正確な表現は次ではありません。

- 「サンドボックスは `/etc` を阻止するから役に立たない」

正しくは次のとおりです。

- 「サンドボックスは shell のデフォルト権限をワークスペースと allowlist の中へ縮小するため、システムレベルのパスへはデフォルトで書き込めない。それによって、プロジェクトはワークスペース内の多数のコマンドを自動的に許可できる。」

## 設計上の境界: 保護するものと保護しないもの

### 保護対象

- Bash / shell コマンドの実行
- 対応プラットフォーム上での PowerShell 実行
- shell サブプロセスがファイルシステムへ書き込める範囲
- shell サブプロセスがネットワークへアクセスできる範囲
- 既知の高リスクパスとサンドボックス脱出ベクトルの一部

### 直接は保護しない対象

- `FileEditTool` / `FileWriteTool` のような直接ファイルを扱うツール
- アプリケーション層だけにある権限ダイアログと規則照合
- Bash AST 解析自体

特に注意すべき点として、Bash AST 解析はサンドボックスではありません。ソースコードに明記されているとおり、答えるのは「argv 構造を信頼できる形で抽出できるか」だけであり、危険なコマンドが実際に実行されることの阻止は担当しません。

## サンドボックスを使う場面

### 1. 起動時に「サンドボックスを利用できるか」を先に判断する

サンドボックスは最初のコマンド実行時まで判断を先送りしません。REPL / CLI の起動時に、現在の環境がサンドボックスの条件を実際に満たしているかを先に確認します。中核となる判定項目は次のとおりです。

1. 現在のプラットフォームを基盤 runtime がサポートしているか
2. 依存関係がすべて揃っているか
3. `sandbox.enabled` が有効か
4. 現在のプラットフォームが `enabledPlatforms` の範囲内か

ユーザーがサンドボックスを明示的に有効化したものの、現在の環境が条件を満たさない場合、起動時に warning を表示します。さらに `sandbox.failIfUnavailable` も設定されていれば、サンドボックスなしのモードへ暗黙にフォールバックせず、起動を直ちに拒否します。

また、起動時は単に「利用できるか確認する」だけではありません。実際に初期化フローを呼び出し、現在の設定を runtime の設定へ変換して、基盤の `BaseSandboxManager.initialize(...)` へ渡します。その後に設定が変われば、セッション全体の再起動を求めず、`updateConfig(...)` で動的に更新します。

### 2. BashTool はデフォルトで使用する

次の条件を満たす限り、Bash コマンドはデフォルトでサンドボックスへ入ります。

1. 現在のプラットフォームがサンドボックスに対応する
2. サンドボックスの依存関係がすべて揃っている
3. `sandbox.enabled` が有効である
4. 現在のプラットフォームが `enabledPlatforms` の範囲内にある
5. 対象コマンドが明示的に除外されていない
6. 今回の呼び出しで `dangerouslyDisableSandbox` による回避が許可されていない

対応するエントリポイントは `packages/builtin-tools/src/tools/BashTool/shouldUseSandbox.ts` と `src/utils/sandbox/sandbox-adapter.ts` です。

### 3. PowerShell は対応プラットフォームでのみ使用する

PowerShell の処理はさらに細かく分かれます。

- Linux / macOS / WSL2: サンドボックスを使用できる
- Windows ネイティブ: サンドボックスに対応せず、`shouldUseSandbox: false` を直接返す

つまり、Windows ネイティブ上の PowerShell は権限システムだけに依存し、OS レベルのサンドボックスによる最後の防御はありません。

### 4. Hook コマンドは「ネットワーク専用サンドボックス」を再利用する

Hook は Bash と同じファイルシステム制限を完全には再利用せず、追加で **network-only sandbox** の層を適用します。

- ネットワークアクセスの阻止を重視する
- ファイルシステムは Bash と同程度まで追加で制限しない

Hook は多くの場合、モデルが直接発行する Bash ツール呼び出しではなく、システムやプラグインの外部拡張ポイントであるためです。

## サンドボックスを使わない場面

### 1. FileEditTool / FileWriteTool

これらのツールは shell 経由でファイルを変更せず、アプリケーション層で直接ファイル I/O を行います。そのため `Shell.exec()` を通らず、当然 `wrapWithSandbox()` にもラップされません。

これらは別の経路を通ります。

- `checkWritePermissionForTool()`
- `checkPathSafetyForAutoEdit()`
- 作業ディレクトリの検査
- allow/ask/deny 規則

したがって、次のようになります。

- 「shell で `/etc/hosts` を変更する」場合、通常はサンドボックスが OS 層で阻止する
- 「FileEdit で `/etc/hosts` を変更する」場合、通常は権限システムがアプリケーション層で阻止する

### 2. 明示的に除外したコマンド

`sandbox.excludedCommands` に一致するコマンドはサンドボックスを直接スキップします。

3 種類のパターンに対応します。

- 厳密一致
- 接頭辞一致
- ワイルドカード一致

### 3. unsandboxed fallback を許可されたコマンド

次の場合です。

- 今回の呼び出しで `dangerouslyDisableSandbox: true` が明示的に設定されている
- ポリシーが `allowUnsandboxedCommands` を許可している

この場合、コマンドはサンドボックスへ入らずに実行できます。

これは意図的に残された設計ですが、名前も意図的に強い表現の `dangerouslyDisableSandbox` です。例外経路であり、デフォルトの習慣にすべきではないと注意を促します。

## 実行フロー全体

プロセス全体は 2 つに分けられます。起動時にサンドボックスを準備し、コマンド実行時に「このコマンドをサンドボックスへ入れるか」を判断します。

### 起動時のフロー

```text
REPL / CLI の起動
  -> isSandboxingEnabled()
  -> convertToSandboxRuntimeConfig(settings)
  -> BaseSandboxManager.initialize(runtimeConfig, callback)
  -> 設定変更時に BaseSandboxManager.updateConfig(newConfig)
```

この部分が答えるのは、現在のセッションに、利用可能で初期化済み、かつネットワーク承認 callback を処理できるサンドボックス runtime があるかという問いです。

### コマンド実行時のフロー

典型的な Bash 実行フローは次のとおりです。

```text
ユーザーの要求
  -> BashTool.checkPermissions()
  -> shouldUseSandbox(input)
  -> Shell.exec(command, { shouldUseSandbox: true/false })
  -> SandboxManager.wrapWithSandbox(...)
  -> spawn(wrapped command)
  -> 実行終了後に cleanupAfterCommand()
```

ここで実際にコマンドを「サンドボックス内へラップする」要点は `Shell.exec()` です。実際の `spawn(...)` の前に `SandboxManager.wrapWithSandbox(...)` を呼び出し、元のコマンドを基盤 runtime が実行できるサンドボックス用のコマンド文字列へ書き換えます。コマンドの終了後、今回が sandboxed execution であれば、さらに `cleanupAfterCommand()` を呼び出してランタイムの残留物を削除します。

ここには混同しやすい 2 つの判定ポイントがあります。

### 判定ポイント A: サンドボックスへ入れるか

これは `shouldUseSandbox()` の役割です。

次の問いに答えます。

> このコマンドを OS レベルのサンドボックスでラップして実行するか？

### 判定ポイント B: このコマンドで権限確認を表示するか

これは権限システムと Bash の権限検査の役割です。

次の問いに答えます。

> アプリケーション層から見て、このコマンドは `allow`、`ask`、`deny` のどれか？

2 つの判定ポイントは並列に連携するものであり、一方が他方を置き換えるものではありません。

## デフォルトのサンドボックスは何を制限するか

サンドボックスのランタイム設定は最終的に `convertToSandboxRuntimeConfig()` が生成します。プロジェクト固有の設定、権限規則、セキュリティ強化ロジックを、基盤ランタイムが必要とする設定へ変換します。

この手順は重要です。このプロジェクトのサンドボックス設定は静的な表ではなく、Claude Code 自身の権限システムから「翻訳」されるためです。

### 権限システムから制限を導出する方法

- `WebFetch(domain:...)` と `sandbox.network.allowedDomains` をネットワーク allowlist へ統合する
- `Edit(...)` / `Read(...)` などの権限規則を、ファイルシステムの読み書き制限へ変換する
- `sandbox.filesystem.allowWrite` / `allowRead` / `denyWrite` / `denyRead` を最終的な runtime 設定へさらに重ねる

つまり、サンドボックスは完全に並行する別のセキュリティポリシーを独立して管理するのではなく、「Claude がどのパスやドメインを許可すべきと判断したか」を OS レベルの制約として実装します。

### ファイルシステムでデフォルトで書き込み可能な範囲

デフォルトの `allowWrite` は 2 種類だけです。

- 現在の作業ディレクトリ `.`
- Claude の一時ディレクトリ

これは次のことを意味します。

- ワークスペース内でのビルド、テスト、一時ファイルの生成は通常どおり実行できる
- `/etc/...`、`/usr/...`、`/var/...` などのルートパスは、デフォルトの書き込み allowlist に含まれない

### ファイルシステムへの書き込みを追加で許可するソース

追加で書き込みを許可するパスは、主に次のソースから得られます。

- `sandbox.filesystem.allowWrite`
- `Edit(...)` 規則から導出したパス
- `/add-dir` または `--add-dir` で追加したディレクトリ
- git worktree のメインリポジトリに必要なパス

見落としやすい点として、アダプター層は worktree のメインリポジトリや bare git repo のようなリポジトリ固有の特殊パスを専用に処理します。分離によって通常の開発フローを壊すことも、逆に脱出経路を残すことも避けるためです。

### 強制的に deny するパス

他の設定が存在しても、プロジェクトはいくつかの高リスクパスをさらに強化します。例は次のとおりです。

- settings ファイル
- `.occ/skills`
- bare git repo に関係する一部のパス

これらのパスが書き込み可能になると、攻撃者が Claude Code 自身の設定、skill、git の挙動を逆に変更し、権限を拡大する可能性があるためです。

### ネットワーク制限

ネットワーク allowlist は 2 つのソースから得られます。

- `sandbox.network.allowedDomains`
- `WebFetch(domain:...)` などの権限規則

許可されたドメインはサンドボックスのネットワーク設定へ入ります。allowlist にないアクセスは実行時に阻止されるか、追加のネットワーク承認フローを開始します。

## `autoAllowBashIfSandboxed` の本当の意味

これはサンドボックス設計で特に注目すべき設定の 1 つです。

次の信頼上の仮定を表します。

> コマンドがすでに OS レベルのサンドボックスによって安全境界内に制約されているなら、アプリケーション層で多数の低リスク Bash コマンドについて個別に確認ダイアログを表示する必要はない。

したがって、この設定が有効な場合は次のように処理します。

- 最初に明示的な `deny` / `ask` 規則を検査する
- これらの強制的な規則に一致しない
- かつコマンドが実際にサンドボックス内で実行される
- この場合、BashTool はコマンドの実行を直ちに自動許可できる

ここには明記すべき境界条件があります。「実際にサンドボックスへ入るコマンド」にしか適用されません。次のような場合は、この shortcut を利用できません。

- `excludedCommands` に一致する
- `dangerouslyDisableSandbox: true` を明示的に使用する
- 現在のプラットフォームがサンドボックスに対応しない

これらのコマンドは OS レベルの制約による安全上の最後の防御を持たないため、引き続き通常の `ask` 規則に従う必要があります。

これがサンドボックスの中核的なプロダクト価値でもあります。より多くの危険な操作を通すのではなく、より多くの**制限範囲内にある通常のコマンド**を意識させずに実行できるようにします。

## 「サンドボックスが `/etc` を阻止する」ことが有用性の証拠である理由

前述の「4 つの中核的な価値」は原理を説明しました。ここでは、デフォルトで `/etc` へ書き込めないシステムの方が信頼に値するのはなぜか、という最も一般的な直感上の疑問へ結論を戻します。

Claude Code が日常的に最も多く実行するのは、システム管理コマンドではなく開発コマンドだからです。たとえば次のようなものです。

- `npm test`
- `npm install`
- `cargo build`
- `pytest`
- `rg`
- `git status`

これらのコマンドは、もともとワークスペースと少数の一時ディレクトリの中でのみ動くべきです。サンドボックスが shell のデフォルト能力をこの範囲まで縮小することで、プロジェクトは初めてアプリケーション層のダイアログを減らし、`autoAllowBashIfSandboxed` を有効にし、自動化の度合いを高められます。

したがって、問うべきなのは「なぜ `/etc` の変更を手伝わないのか」ではなく、「`/etc` に触れないまま、多数の通常の開発コマンドをより安全かつ円滑に実行できるか」です。この観点では、デフォルトで `/etc` へ書き込めないことは欠点ではなく、自動化された体験全体が成立する前提です。

## プラットフォームによる違い

### macOS

- 基盤では `sandbox-exec` を使用する
- パスとネットワークの規則を Seatbelt profile で実装する
- OS ネイティブのプロセス分離に該当する

### Linux

- 基盤では `bubblewrap + seccomp` を使用する
- mount / PID / network などを分離する
- Linux の glob パス対応は macOS より弱い
- 実行後の一部の残留物は `cleanupAfterCommand()` で削除する必要がある

### WSL

- WSL2 のみ対応する
- WSL1 は非対応プラットフォームとして扱う

### Windows ネイティブ

- ネイティブの PowerShell/Bash はこのサンドボックスシステムに対応しない
- したがって、権限システムとツールレベルの検査だけに依存する

このため、「C ドライブのファイルを変更するとサンドボックスを使うか」という質問への答えは次のように分かれます。

- Windows ネイティブ: 通常は使わない
- Linux/macOS/WSL2: shell の場合にのみ使う可能性がある

## ワークスペースの内外: アプリケーション層とサンドボックス層の連携

### ワークスペース内のパス

ワークスペース内のパスには通常、2 層の保護があります。

1. アプリケーション層の権限検査
2. サンドボックスはデフォルトで現在の作業ディレクトリへの書き込みを許可

これにより、「ワークスペース内でのビルド、テスト、フォーマット、ファイル生成」が最も円滑な経路になります。

### ワークスペース外のパス

ワークスペース外のパスはさらに厳しく扱われます。

- アプリケーション層では通常、高リスクと見なして確認を求めるか阻止する
- アプリケーション層が許可しても、サンドボックスの allowlist に含まれなければ実行時に失敗する

これにより 2 重の防御を形成します。

### Linux のルートパス `/etc/...`

Linux のルートパスにあるファイルでは、通常は次の 2 通りになります。

- **shell の経路**: コマンドはサンドボックスへ入るが、サンドボックスはデフォルトで `/etc` への書き込み権限を持たないため、実行時に阻止される
- **ファイルツールの経路**: サンドボックスを使わず、アプリケーション層のファイル権限検査で直接阻止される

## ユーザーが実際に目にするもの

阻止された場合の体験は一様ではなく、少なくとも 3 種類あります。

### 1. 実行前の権限確認

アプリケーション層が実行前に `ask` と判定した場合、ユーザーには標準の権限ダイアログが表示されます。

- Bash の権限確認
- FileEdit / FileWrite の権限確認
- その他のツール固有の権限確認 UI

このプロンプトは、コマンドが実際に実行される前に表示されます。

### 2. 実行中のサンドボックス違反

コマンドがすでにサンドボックスへ入り、実行時に違反が発生した場合は次のようになります。

- コマンドが失敗する
- モデルが理解できるよう、stderr に `<sandbox_violations>` タグを付加する
- UI はこれらのタグを取り除いてからユーザーへ表示する
- 同時に `SandboxViolationStore` が違反イベントを記録する

つまり、ユーザーには通常、次の内容が表示されます。

- コマンド自体の失敗
- 「直近で sandbox blocked が何回発生したか」といった UI の通知

### 3. ネットワーク境界外への要求

ネットワークは例外です。

サンドボックス外の host へのアクセスに追加の確認が必要な場合、プロジェクトは次のような専用のネットワーク承認ダイアログを表示します。

- `Network request outside of sandbox`

ファイルシステムに対する実行時の阻止とは異なり、ここには明示的な対話型の承認 UI があります。

## ファイルシステムの境界外アクセスで通常「今回だけ許可」を表示しない理由

これは明確な意図に基づく設計上の選択です。

ファイルシステムに対して、プロジェクトは次の方式を優先します。

- 実行前にアプリケーション層で ask にする
- または実行後にサンドボックスによってコマンドをそのまま失敗させる

実行途中に「このシステムパスへの書き込みを許可するか」という新たなダイアログを表示する方式は選びません。

この設計には次の利点があります。

- 境界が安定する
- ユーザーのメンタルモデルが明確になる
- shell の実行環境を段階的に拡張し、次第に緩くする事態を避けやすい

ネットワークアクセスは host 単位の一時的な承認に適しているため、専用の承認ダイアログを用意しています。

## よくある誤解

### 誤解 1: サンドボックスはすべてのファイル変更を保護する

違います。主に保護するのは **shell サブプロセス**です。

直接ファイルを編集するツールは、shell サンドボックスではなくアプリケーション層の権限システムを通ります。

### 誤解 2: サンドボックスを有効にすれば、権限システムは不要になる

違います。サンドボックスはプロセスの能力だけを制限し、ユーザーの意図、パスの安全性に関する意味、ツールモード、承認体験を解釈しません。

プロジェクトが複雑な `allow / ask / deny` システムを維持しているのは、両者の役割が異なるためです。

### 誤解 3: 危険な操作をサンドボックスが阻止したなら、アプリケーション層の検査には価値がない

違います。アプリケーション層の検査には次の価値があります。

- より早く通知する
- ユーザー体験を改善する
- より細かな意味に基づいて判断する
- shell を使わないツールにも適用できる

サンドボックスは最終的な防御を担当します。

## 推奨する読み進め方

ソースコードをさらに詳しく追う場合は、次の順序を推奨します。

1. `packages/builtin-tools/src/tools/BashTool/shouldUseSandbox.ts`
2. `src/utils/Shell.ts`
3. `src/utils/sandbox/sandbox-adapter.ts`
4. `src/utils/permissions/permissions.ts`
5. `packages/builtin-tools/src/tools/BashTool/bashPermissions.ts`
6. `src/utils/permissions/pathValidation.ts`
7. `src/utils/permissions/filesystem.ts`

この順序で読めば、「権限システム」と「サンドボックスシステム」を頭の中で分けて理解しやすくなります。

## FAQ

### Q1: Linux で `echo hi > /etc/hosts` を実行するとどうなるか？

BashTool の場合:

- 通常はサンドボックスへ入る
- デフォルトのサンドボックスは `/etc` への書き込みを許可しない
- そのため、コマンドは実行時に失敗する

FileEditTool の場合:

- サンドボックスへ入らない
- 通常は先にアプリケーション層のファイル権限検査で阻止される

### Q2: Windows で `C:\Windows\System32\drivers\etc\hosts` を変更するとどうなるか？

Windows ネイティブ環境では通常、この shell サンドボックスによる最後の防御がないため、主にアプリケーション層の権限システムとツール固有の検査ロジックに依存します。

### Q3: サンドボックスがこれほど強力なのに、なぜ `dangerouslyDisableSandbox` を残すのか？

実際の開発タスクには、デフォルト境界の外へ出る必要があるものも存在するためです。たとえば次のような場合です。

- allowlist に追加されていないツールチェーンのディレクトリへアクセスする
- システムレベルの環境をデバッグする
- 管理者が明示的に許可した例外操作を行う

ただし、プロジェクトはこのエントリポイントを非常に目立つ形にしており、管理者がポリシーで直接無効化することもできます。デフォルトの経路になることを防ぐためです。

### Q4: サンドボックスの価値を最も実感できるのはいつか？

`autoAllowBashIfSandboxed` を有効にしたときに最も明確になります。

この場合、ワークスペース内の多数のコマンドはダイアログを減らすか、まったく表示せずに実行できます。それでも、モデルが境界外のコマンドを生成した場合、システムレベルの書き込み能力とネットワーク能力は引き続き境界によって制限されます。

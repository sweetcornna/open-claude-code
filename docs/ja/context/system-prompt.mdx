## 配列から API 呼び出しまで

システムプロンプトは固定のテキストではありません。**`string[]`**（ブランド型 `SystemPrompt`）であり、組み立て、ブロック分割、キャッシュ用の印付けを経て API へ送られます。

### 3 段のパイプライン

```
getSystemPrompt()            →  string[]         （内容を集める）
  ↓
buildEffectiveSystemPrompt() →  SystemPrompt     （優先順位の経路を選ぶ）
  ↓
buildSystemPromptBlocks()    →  TextBlockParam[] （分割 + cache_control）
```

1. **`getSystemPrompt()`**（`src/constants/prompts/assemble.ts`）が静的・動的セクションを集め、`SYSTEM_PROMPT_DYNAMIC_BOUNDARY` を挿入する
2. **`buildEffectiveSystemPrompt()`**（`src/utils/session/systemPrompt.ts`）が Override > Coordinator > Agent > Custom > Default から選ぶ
3. **`buildSystemPromptBlocks()`**（`src/services/api/claude.ts`）が `splitSysPromptPrefix()` で分割し、各ブロックに `cache_control` を付ける

## ブランド型

```typescript
// packages/@ant/model-provider/src/types/systemPrompt.ts
export type SystemPrompt = readonly string[] & {
  readonly __brand: 'SystemPrompt'
}
export function asSystemPrompt(value: readonly string[]): SystemPrompt {
  return value as SystemPrompt  // ゼロコストの型アサーション
}
```

ブランドにより、素の `string[]` が誤って API 呼び出しへ渡ることを防ぎます。`asSystemPrompt()` を明示的に通したものだけがこの型になります。`src/utils/session/systemPromptType.ts` は後方互換のための再エクスポート層で、定義本体は上のパッケージ側にあります。

## `src/constants/prompts/` のモジュール構成

`src/constants/prompts.ts` はかつて 900 行の単一ファイルでしたが、現在は**ロジックを持たない純粋な再エクスポート barrel** です。十数か所の既存 import をそのまま動かすためだけに残っています。プロンプト本体は関心ごとに `src/constants/prompts/` へ分割され、1 セクション 1 モジュールになりました。

| ファイル | 置くもの |
|---------|---------|
| `assemble.ts` | `getSystemPrompt()`：セクションの順序、静的／動的境界の位置、2 つの早期 return 経路（`CLAUDE_CODE_SIMPLE` と proactive）、`TOKEN_BUDGET_SECTION` |
| `shared.ts` | 2 つ以上のセクションが一字一句共有する定数：`SYSTEM_PROMPT_DYNAMIC_BOUNDARY`、`EMOJI_GUIDANCE`、`NO_COLON_BEFORE_TOOL_CALLS`、`SUMMARIZE_TOOL_RESULTS_SECTION` |
| `format.ts` | 描画ヘルパー：`prependBullets()`（意味を担う ` - ` / `  - ` の入れ子）と `bulletSection()`（`# 見出し` + 箇条書き。中身が全て消えたら `null`） |
| `intro.ts` | 冒頭ブロック、サイバーリスク指示、URL の制約。**製品アイデンティティ行はここにはありません** —— `getCLISyspromptPrefix()`（`src/constants/system.ts`）が前置します |
| `harness.ts` | `# System`：モデル自身では観測できない harness の事実（出力がユーザーへ届く経路、権限モード、コアツールと遅延ツール、`<system-reminder>` タグ、prompt injection、hooks） |
| `doingTasks.ts` | `# Doing tasks`：タスクの範囲、コードスタイルとコメントの規律、正直な報告、フィードバック導線 |
| `actions.ts` | `# Executing actions with care`：可逆性と影響範囲、リスク行為の分類、git の事前確認 |
| `tools.ts` | `# Using your tools` と `getAgentToolSection()`、および 2 つの `CORE_TOOLS_PROMPT_*_NAMES` 一覧 |
| `communication.ts` | `# Communicating with the user` —— **ユーザーに見えるテキストのみ**（ツール呼び出しの合間の更新、最終回答の形、コード参照の記法） |
| `conduct.ts` | 行動規範のセクション群：`# Delivering work`、`# Corrections`、`# Context management`、および見出しのない独立ルール 3 本（代名詞の既定、タスクの連続性、情報が揃ったら動く） |
| `sessionGuidance.ts` | `# Session-specific guidance`：そのセッションで使えるものによって変わる指針（境界より後に置く必要がある） |
| `environment.ts` | `# Environment` と `computeSimpleEnvInfo()`、知識カットオフ表、シェル判定 |
| `preferences.ts` | `# Language` と `# Output Style: <name>` |
| `mcp.ts` | `# MCP Server Instructions`（サーバー名でソートしてから連結） |
| `scratchpad.ts` | `# Scratchpad Directory` |
| `discoverSkills.ts` | DiscoverSkills の文言と feature 判定。メインセッションとサブエージェントで共有 |
| `subagent.ts` | `DEFAULT_AGENT_PROMPT`、サブエージェントの権限境界、`enhanceSystemPromptWithEnvDetails()`。**`getSystemPrompt()` の出力には含まれません** |
| `proactive.ts` | 自律モード（proactive / KAIROS）の骨格一式と `brief` セクション |

**追加するときの置き場所**（barrel 冒頭のコメントがそのまま 3 か条です）:

- 新しいプロンプトのセクション → `./prompts/` 配下の**専用モジュール**
- 順序やキャッシュ境界の調整 → `./prompts/assemble.ts`
- 2 つのセクションが共有する文字列 → `./prompts/shared.ts`

`src/constants/prompts.ts` 自体はもうロジックを受け付けません。

> **改名されたセクション。** 旧版の「Tone & Style」と「Output Efficiency」は、単一の `# Communicating with the user` に統合されました。ant 限定の「Model Override」（`defaultSystemPromptSuffix`）は連鎖ごと削除され、ガードレールに逆方向のアサーションが入っています。「FRC」セクションはもう存在しません。

## `getSystemPrompt()` が組み立てるもの（実際の描画順）

`getSystemPrompt()` は順序付きの配列を返し、最終的に `\n\n` で連結されます。下表は**実際の描画順**です。`bun run scripts/dump-prompt.ts` でいつでも取り直せます（完全な出力が `scripts/system-prompt-dump.txt` に書かれます。`.gitignore` 済みのスクリプト生成物なので、コミットしないでください）。

「見出しなし」の項目は本当に `#` 見出しを持ちません。隣のセクションの箇条書きではなく、1 ルールで独立したブロックです。

### 境界の印

`SYSTEM_PROMPT_DYNAMIC_BOUNDARY`（`= '__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__'`、`shared.ts` に定義）は 13 番の直後に入り、**`shouldUseGlobalCacheScope()` が真のときだけ**挿入されます。これは番兵の文字列で、送信前に取り除かれるためモデルが目にすることはありません。役割は、分割処理が静的領域だけを正確に `scope: 'global'` と印付けできるようにすることです。

### 動的領域（境界より後、セクションレジストリ経由）

| # | 描画される見出し | モジュール | 登録名 |

| 16 | `# Environment` | `environment.ts` | `env_info_simple` |
| 17 | `# Language` | `preferences.ts` | `language`（言語設定が無ければ null） |
| 18 | `# Output Style: <name>` | `preferences.ts` | `output_style` |
| 19 | `# MCP Server Instructions` | `mcp.ts` | `mcp_instructions`（唯一の `DANGEROUS_uncached`） |
| 20 | `# Scratchpad Directory` | `scratchpad.ts` | `scratchpad` |
| 21 | *（見出しなし）* トークン予算 | `assemble.ts` | `token_budget`。`TOKEN_BUDGET` のコンパイルが必要 |
| 22 | *（見出しなし）* brief モード | `proactive.ts` | `brief`。`KAIROS` または `KAIROS_BRIEF` が必要 |

動的セクションのほとんどは**条件付き**です。既定設定で取った dump には、静的領域の全項目に加えて `# Session-specific guidance` と `# Environment` の 2 つしか現れません。残りは言語設定なし・output style なし・MCP サーバーなし・scratchpad 無効・feature 未コンパイルのため `null` を返し、除外されます。

## 静的と動的の分け方（および occ と上流の相違）

`assemble.ts` の JSDoc は、静かに壊れうる不変条件を 2 つ関数の頭に書いています。

1. **境界より前はすべてビルド時定数でなければならない。** その前置部分はハッシュ化され、*組織をまたいで*キャッシュされます。実行時ビットで文面が変わるセクションは印より後に置くべきで、さもないとキャッシュキーの変種が 2^N 倍に膨らみます。
2. **印より後のセクションはセクションレジストリを通る**ため、会話ごとにメモ化され、`/clear` と `/compact` で無効化されます。

**ここが occ と上流の意図的な相違点です。** 上流は行動規範のセクション（代名詞、`# Delivering work`、`# Corrections`、`# Context management`）を動的側に置いています。ゲートが Anthropic の A/B フラグを読み、「これは Claude のモデルファミリーか」という判定と AND を取るからです。occ にはファーストパーティ経路の外で**そのどちらの入力もありません**。ゲートをそのまま移植すれば、多くの provider でこれらのセクションが黙って空になります。そこで occ はこれらをすべての provider に**無条件**で適用します。結果としてビルド時定数になるため、キャッシュ可能な側に置くのが正しい、というわけです。意図的な相違であって、見落としではありません。

同じ理由で、もともとただの定数文字列だった `SUMMARIZE_TOOL_RESULTS_SECTION` も、動的スロットを 1 つ占めるのをやめて静的領域へ移りました。

逆に `# Session-specific guidance` の中の条件 —— `enabledTools` の集合、`isForkSubagentEnabled()`、`getIsNonInteractiveSession()`、GrowthBook のゲート値 —— はどれも実行時ビットなので、境界より後に留める必要があります。ソースのコメントも率直です。

> Everything here must stay AFTER SYSTEM_PROMPT_DYNAMIC_BOUNDARY. Each conditional is a runtime bit that would otherwise multiply the Blake2b prefix-hash variants of the cacheScope:'global' prefix (2^N).

### 動的セクションの登録

動的セクションは `systemPromptSection()` か `DANGEROUS_uncachedSystemPromptSection()` で登録します。いずれも `src/constants/systemPromptSections.ts` にあります。

```typescript
// キャッシュされる: 一度計算し、/clear や /compact の後にだけ再計算する
systemPromptSection('memory', () => loadMemoryPrompt())

// 危険: 毎ターン再計算するのでプロンプトキャッシュを壊す
DANGEROUS_uncachedSystemPromptSection(
  'mcp_instructions',
  () => isMcpInstructionsDeltaEnabled() ? null : getMcpInstructionsSection(mcpClients),
  'MCP servers connect/disconnect between turns'  // 理由の記載が必須
)
```

`resolveSystemPromptSections()` が毎ターンすべてのセクションを解決し、`cacheBreak: false` のものは `getSystemPromptSectionCache()` のキャッシュ値を優先します。プロンプト全体で危険な方を使うのは MCP 指示だけです。しかもそのゲート判定は、2 つのセクション変種を選び分けるのではなく compute 関数の**内側**にあります。こうしておけば、セッション途中でゲートが反転しても古いキャッシュ値を読むことがありません。

## 2 つの早期 return 経路

`getSystemPrompt()` には、上の表に至らない分岐が 2 つあります。

### `CLAUDE_CODE_SIMPLE` の高速経路

`CLAUDE_CODE_SIMPLE` が設定されていると、プロンプト全体が 1 行になります。

```typescript
`You are Claude Code, Anthropic's official CLI for Claude.\n\nCWD: ${getCwd()}\nDate: ${getSessionStartDate()}`
```

セクション登録もキャッシュ分割も動的な組み立ても飛ばします。トークン消費を最小にしたいテスト用です。

### proactive（自律モード）の経路

`isProactiveActive()` が真のとき、静的な骨格はまるごと差し替えられます。tick プロンプトで駆動されるエージェントは対話的なエージェントとは仕事の形が違うため、`# Doing tasks` や `# Using your tools` を**継承しません**。この経路が出すのは、`PROACTIVE_INTRO` とサイバーリスク指示、`<system-reminder>` の説明、`# Context management`、メモリ、環境、言語、MCP 指示、scratchpad、ツール結果のルール、そして最後に `getProactiveSection()` の `# Autonomous work` です。

## 5 段階の優先順位

`src/utils/session/systemPrompt.ts` が実際に使うプロンプトを決めます。

| 優先度 | 条件 | 挙動 |
|--------|------|------|
| **0. Override** | `overrideSystemPrompt` が空でない | 完全に置き換え、`[override]` を返す |
| **1. Coordinator** | `COORDINATOR_MODE` feature と対応する環境変数 | coordinator 用のプロンプトを使う |
| **2. Agent** | `mainThreadAgentDefinition` がある | proactive モードでは既定の末尾へ追記、それ以外は置き換え |
| **3. Custom** | `--system-prompt` が指定された | 既定を置き換える |
| **4. Default** | 特別な条件なし | `getSystemPrompt()` の完全な出力 |

`appendSystemPrompt` は常に末尾へ追加されます（Override のときを除く）。

## provider

occ は複数の API provider に対応し、2 つに分かれます。

| 区分 | Provider | 環境変数 | 備考 |
|------|----------|---------|------|
| **1P（ファーストパーティ）** | `firstParty` | 既定 | Anthropic の API に直接 |
| **3P** | `bedrock` | `CLAUDE_CODE_USE_BEDROCK=1` | AWS Bedrock |
| **3P** | `vertex` | `CLAUDE_CODE_USE_VERTEX=1` | Google Vertex AI |
| **3P** | `openai` | `CLAUDE_CODE_USE_OPENAI=1` | OpenAI 互換レイヤ（Ollama / DeepSeek / vLLM） |
| **3P** | `gemini` | `CLAUDE_CODE_USE_GEMINI=1` | Google Gemini |
| **3P** | `grok` | `CLAUDE_CODE_USE_GROK=1` | xAI Grok |

```typescript
// src/utils/model/providers.ts
export type APIProvider =
  | 'firstParty'
  | 'bedrock'
  | 'vertex'
  | 'foundry'
  | 'openai'
  | 'gemini'
  | 'grok'
```

**`getAPIProvider()` が答えるのは「どの通信形式か」であって、「このセッションが誰のものか」ではありません。** 3 つの別々の問いに 3 つの別々の述語があり、取り違えてはいけません。

- `getAPIProvider()` —— どのプロトコルで話すか
- `isThirdPartyModelCatalog()` —— 誰のカタログか、誰の価格表か。**グローバルキャッシュのゲートはこれ**
- `servesAnthropicModels()` —— `claude-opus-5` という id が本当に Anthropic の Opus 5 を指すか。**環境セクションのモデルカタログ行のゲートはこれ**

provider は、使える beta ヘッダ（一部はファーストパーティのカタログ限定）とトークンの数え方（Bedrock は専用の countTokens、OpenAI と Gemini は概算）も決めます。

## 環境セクションの provider 中立化

`# Environment`（`computeSimpleEnvInfo()`）は、プロンプト中で唯一「どのモデルで動いているか、どんなマシンか」を述べる場所です。つまり、Anthropic 以外のセッションに嘘をつきやすい場所でもあります。ゲートは 3 つです。

- **マーケティング名**：`getMarketingNameForModel()` は、そのセッションが Anthropic のチェックポイントを提供していなければ `undefined` を返し、行は `You are powered by the model <id>.`（マーケティング名なしの素の id）になります。
- **Claude モデルカタログ行**（「Model IDs — Fable 5: …」）のゲートは **`servesAnthropicModels()`** です。`getAPIProvider()`（通信形式の答え）でも `isThirdPartyModelCatalog()`（価格表の答え）でもありません。Bedrock / Vertex / Foundry は本物の Claude チェックポイントを提供するのでこの行が要ります。一方 OpenAI 互換エンドポイントでは `claude-opus-5` が「提供していない単なる文字列」に解決されるため、その id をモデルに渡すことは、必ず 404 になる API 文字列をユーザーのコードへ書かせるのと同じです。
- **fast mode の行**のゲートは `isFastModeAvailable()` で、第三者カタログ判定と購読判定がすでに畳み込まれています。ユーザーが押せないトグルをモデルに宣伝しても、実行できない提案が生まれるだけです。

Anthropic の製品ラインナップの一文（デスクトップ / ウェブ / ブラウザ拡張）はこのビルドでは事実に反するため**削除済み**で、ガードレールに逆方向のアサーションがあります。サブエージェントは `includeProductInfo: false` を通るので、カタログ行も fast mode 行も受け取りません。

知識カットオフ表（`getKnowledgeCutoff()`）は手動管理です。上流はモデルカタログの `knowledge_cutoff` フィールドから読みますが、occ はそのカタログデータを持ちません（`ALL_MODEL_CONFIGS` にあるのは id だけです）。

## キャッシュ: ブロック、印、命中

設計の中で最も緻密な部分です。

### 前提

Anthropic のプロンプトキャッシュは、同一のシステムプロンプト前置部分をリクエストをまたいで再利用し、命中分を通常の入力より大幅に安く課金します。キャッシュキーは内容の Blake2b ハッシュなので、1 文字変われば無効になります。

### `splitSysPromptPrefix()` の 3 モード

キャッシュ戦略の中心は `src/utils/telemetry/api.ts` の `splitSysPromptPrefix()` です。attribution ヘッダと CLI 前置ブロックは、位置ではなく**内容**で識別します（`CLI_SYSPROMPT_PREFIXES`）。

**モード 1 — MCP ツールがある場合（`skipGlobalCacheForSystemPrompt=true`）**

```
[attribution header]    → cacheScope: null    （キャッシュなし）
[system prompt prefix]  → cacheScope: 'org'
[everything else]       → cacheScope: 'org'
```

MCP のツール一覧はサーバーの接続・切断でセッション途中に変わりえます。組織をまたぐキャッシュの前提が崩れるため、組織スコープへ格下げされます。この経路では境界の印はそのまま捨てられます。

**モード 2 — グローバルキャッシュ + 境界あり**

```
[attribution header]    → cacheScope: null     （キャッシュなし）
[system prompt prefix]  → cacheScope: null     （キャッシュなし）
[static content]        → cacheScope: 'global' （組織をまたいで共有）
[dynamic content]       → cacheScope: null     （キャッシュなし）
```

最も効率の良いモードです。`SYSTEM_PROMPT_DYNAMIC_BOUNDARY` より前（intro、`# System`、`# Doing tasks`、`# Communicating with the user`、行動規範の各節）は全ユーザー共通なので、グローバルにキャッシュできます。

> **境界が挿入される条件:**

```typescript
// src/utils/model/betas.ts
export function shouldUseGlobalCacheScope(): boolean {
  return (
    !isThirdPartyModelCatalog() &&
    !isEnvTruthy(process.env.CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS)
  )
}
```

```typescript
// src/constants/prompts/assemble.ts
...(shouldUseGlobalCacheScope() ? [SYSTEM_PROMPT_DYNAMIC_BOUNDARY] : []),
```

つまり:

- **第三者カタログのセッション**（Bedrock / Vertex / Foundry / OpenAI / Gemini / Grok / OpenCode など）には境界が存在せず、常にモード 3 です。Foundry が外れているのは、GrowthBook が Foundry ユーザーをロールアウト実験に振り分けたことがなく、treatment データがファーストパーティ分しかないからです。
- **実験的 beta を切った場合**（`CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1`）にも境界は入りません
- **それ以外**は境界あり、モード 2

判定に使うのは `isThirdPartyModelCatalog()` であって `getAPIProvider() === 'firstParty'` ではない点に注意してください。`claude-*` 系モデルを配る単純なプロキシや企業ゲートウェイは第三者カタログではないので、グローバルキャッシュを受け取れます。

**モード 3 — 既定（第三者カタログ、または境界なし）**

```
[attribution header]    → cacheScope: null    （キャッシュなし）
[system prompt prefix]  → cacheScope: 'org'
[everything else]       → cacheScope: 'org'
```

### `getCacheControl()` と TTL

`src/services/api/claude.ts` の `getCacheControl()` が `cache_control` を作ります。

```typescript
{
  type: 'ephemeral',
  ttl?: '1h',         // 資格のある querySource のみ
  scope?: 'global',   // 静的領域のみ
}
```

1 時間 TTL は `should1hCacheTTL()` が決めます。

- **Bedrock ユーザー** — `ENABLE_PROMPT_CACHING_1H_BEDROCK` で有効化
- **明示的な上書き** — `CLAUDE_CODE_PROMPT_CACHING_1H=1` は資格の無いユーザー（自前の API key など）にも 1h TTL を与え、`=0` は 5m へ強制します。**どちらの方向も、以下の資格判定と allowlist より優先されます。** 従量課金の key で 1h 書き込みの 2 倍加算を切る唯一の手段が `=0` です。
- **資格** — 社内ユーザー、または超過状態でない Claude 購読者（購読者の 1h 書き込みに追加費用はかかりません）
- **allowlist** — `querySource` が GrowthBook の `allowlist` 配列に一致する必要があります。末尾のワイルドカード（`"repl_main_thread*"` など）に対応します。**GrowthBook が設定を配信しない場合**は `PROMPT_CACHE_1H_DEFAULT_ALLOWLIST`（`src/services/api/promptCacheTTL.ts`: メインスレッド / compact / sdk / サブエージェント）へ戻ります。明示的に空配列が配信された場合は「全員無効」の意味を保ち、遠隔のキルスイッチは機能し続けます。
  - 以前はここが `[]` に戻っていたため、Anthropic 社内のデプロイ以外では 1h TTL が実質的な死にコードでした。**5 分を超える停止のたびに 20〜50K トークンの前置部分が丸ごと書き直されていた**ことになります。短命な fork 元（`speculation`、`session_memory`、`prompt_suggestion`）は既定表から意図的に外しています。1〜3 ターンしか動かないため、1h の書き込みは費用だけ払って読み戻せません。
- **セッション内の安定性** — 資格判定の結果は bootstrap state に固定され、GrowthBook の設定が途中で変わっても同一セッション内で TTL がぶれません

## コンテキストの注入

システムプロンプトの配列には実行時の文脈（git の状態、CLAUDE.md）は入りません。それらは別の 2 経路から入り、どちらも `src/context.ts` にあります。

### システムコンテキスト（`getSystemContext()`）

```typescript
export const getSystemContext = memoize(async () => {
  return {
    gitStatus,           // ブランチ、状態、直近のコミット
    cacheBreaker,        // BREAK_CACHE_COMMAND がコンパイルされている場合のみ
  }
})
```

- `lodash.memoize` により、**セッション中に 1 度だけ**計算されます
- git のスナップショットは 5 つの `git` コマンドを並列実行します（branch、defaultBranch、status、log、userName）
- status が `MAX_STATUS_CHARS`（1000 文字）を超えると切り詰め、BashTool でさらに見るよう注記を付けます
- `CLAUDE_CODE_REMOTE` が真の場合、または git の指示が無効な場合は git 状態を丸ごと省略します
- `setSystemPromptInjection()` は `getUserContext` と `getSystemContext` 両方のキャッシュを即座に消します

### ユーザーコンテキスト（`getUserContext()`）

```typescript
export const getUserContext = memoize(async () => {
  return {
    claudeMd,            // 統合済みの CLAUDE.md
    currentDate,         // "Today's date is YYYY-MM-DD."
  }
})
```

- CLAUDE.md は `CLAUDE_CODE_DISABLE_CLAUDE_MDS` で無効になります。`--bare` でも無効ですが、`--add-dir` で明示指定したディレクトリは例外です
- `--bare` の意味は「頼んでいないものは飛ばす」であり、「すべてを無視する」ではありません

### 注入される位置

`src/query.ts` にて:

```typescript
// システムコンテキストはシステムプロンプトの末尾へ追加する
const fullSystemPrompt = asSystemPrompt(
  appendSystemContext(systemPrompt, systemContext)  // 単純な連結
)
```

ユーザーコンテキストは `prependUserContext()`（`src/utils/telemetry/api.ts`）が、会話のすべてのメッセージより前に置かれる最初の user メッセージとして、`<system-reminder>` タグで包んで注入します。

## attribution ヘッダ

すべてのリクエストのシステムプロンプトの先頭ブロックが attribution ヘッダです（`src/constants/system.ts` の `getAttributionHeader()`）。

- **`cc_version`** — occ のバージョン
- **`cc_entrypoint`** — 動作している入口（REPL / SDK / pipe など。`CLAUDE_CODE_ENTRYPOINT` から読む）
- **`cc_workload`** — ターン単位のヒント。cron 起点のリクエストなどを低 QoS のプールへ振り分けるために使う。無い場合は対話的な既定
- **`cch=00000`** — `NATIVE_CLIENT_ATTESTATION` が有効なとき、Bun のネイティブ HTTP 層が送信前にゼロを計算済みハッシュへ置き換え、サーバーがそれを検証して本物のクライアントからの要求であることを確認する。同じ長さのプレースホルダにしているのは、Content-Length の変化とバッファ再確保を避けるため

このヘッダは常に `cacheScope: null` です。バージョンと入口で変わるため、キャッシュしても意味がありません。`CLAUDE_CODE_ATTRIBUTION_HEADER=0` か GrowthBook のキルスイッチで丸ごと止められます。

## CLAUDE.md

プロジェクト根に `CLAUDE.md` を置くだけで、モデルがそのプロジェクトを理解します。

- **概要** — 何をするプロジェクトで、何の上に建っているか
- **規約** — コードスタイル、命名、ブランチ運用
- **コマンド** — ビルド、テスト、デプロイの方法
- **落とし穴** — 既知の罠、特殊な設定

複数階層が自動で発見・統合されます。

```
~/.occ/CLAUDE.md                    ← ユーザー全体（個人の好み）
  └── /project/CLAUDE.md            ← プロジェクト根（チーム共有）
        └── /project/src/CLAUDE.md  ← サブディレクトリ（モジュール固有）
```

`src/utils/session/claudemd.ts` の `getClaudeMds()` と `getMemoryFiles()` が作業ディレクトリから上へ辿り、一致するものをすべて統合します。

## なぜ 1 つの `string` ではなく `string[]` なのか

配列としてモデル化しているのは**キャッシュのブロック化**のためです。

1. Anthropic のプロンプトキャッシュは**コンテンツブロック**単位で働く
2. 分割することで、変わらない部分（intro、`# System`）が独立して命中できる
3. 1 つの `string` だと、日付が変わるといった 1 文字の違いでプロンプト全体のキャッシュが無効になる
4. `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` により `splitSysPromptPrefix()` が静的領域だけを `scope: 'global'` と印付けし、動的領域はキャッシュなしか `scope: 'org'` にできる

これがトークンコスト最適化の中心です。典型的なシステムプロンプトは 20K トークン超あり、ブロック化により入力トークン費用の 30〜50% を節約できます。

## プロンプトを編集するときのガードレール

3 つあり、どれを欠いても見落とされる変更の種類が生まれます。

- **`bun run scripts/dump-prompt.ts`** は完全なプロンプトを `scripts/system-prompt-dump.txt` へ描画します（`.gitignore` 済みのスクリプト生成物。コミットしないこと）。変更の前後で 1 回ずつ実行して差分を取ることが、「モデルが実際に何を受け取るか」を見る唯一の手段です。単体テストはいくつかのアンカー文を検査するだけで、セクションの順序、空行、ゲートで丸ごと消えた節までは見えません。第 1 引数にモデル id を渡せます。
- **`src/constants/promptEngineeringAudit.runner.ts`** は、挙動のアンカー、削除済み内容への逆方向アサーション（Anthropic の製品ラインナップ、ant 限定の `defaultSystemPromptSuffix` など）、構造アサーション（静的セクションの順序、`# Session-specific guidance` と `# Environment` が境界より前に現れないこと）を保持します。
- **`tests/mocks/systemPromptEnv.ts`** は dump スクリプトとガードレール runner が共有するモック連鎖です。ここでの上書きはすべて出力を*決定的*にするため（ホストの provider 設定、git の状態、feature flag、端末に左右されないため）にあり、何かを握りつぶすためではありません。以前は 2 つの呼び出し側が手書きの複製を持っており、案の定ずれました。

## OpenAI / Gemini 互換レイヤ

occ は OpenAI・Gemini・Grok の各プロトコルに互換レイヤを持ち、Anthropic 以外のエンドポイントを使えます。コードは 2 か所に分かれます。**プロトコル・認証・ネットワーク**は `src/services/api/<provider>/`、**フォーマット変換**は `packages/@ant/model-provider/src/providers/<provider>/` です。

### OpenAI

`CLAUDE_CODE_USE_OPENAI=1` で有効になります。実体は**ストリームアダプタ**です。

1. Anthropic 形式のリクエストを OpenAI 形式へ変換する
2. 互換エンドポイントを呼ぶ
3. SSE ストリームを `BetaRawMessageStreamEvent` へ戻す
4. 下流はこの一切を意識しない

```
src/services/api/openai/
├── client.ts             # クライアント設定
├── wireProtocol.ts       # chat / responses 2 本の線の選択
├── requestBody.ts        # リクエストボディの構築
├── responsesAdapter.ts   # Responses API の適合（アイドル監視、プロキシ対応）
├── retry.ts              # バックオフ再試行
├── reasoning.ts          # reasoning / effort パラメータ
├── gptBehaviorPrompt.ts  # GPT 系の挙動オーバーレイ
├── chatgptAuth.ts        # ChatGPT 購読の認証
└── index.ts              # 入口関数 queryModelOpenAI()
```

主な環境変数: `CLAUDE_CODE_USE_OPENAI=1`、`OPENAI_API_KEY`、`OPENAI_BASE_URL`（既定 `https://api.openai.com/v1`）、`OPENAI_MODEL`、`OPENAI_WIRE_API`（既定 `chat`、または `responses`）。

### Gemini

`CLAUDE_CODE_USE_GEMINI=1` で有効になります。

```
src/services/api/gemini/           packages/@ant/model-provider/src/providers/gemini/
├── client.ts                      ├── convertMessages.ts  # メッセージ変換
├── oauthToken.ts                  ├── convertTools.ts     # ツール定義の変換
├── antigravityWire.ts             ├── streamAdapter.ts    # ストリーム変換
├── reasoning.ts                   ├── modelMapping.ts     # モデル名の対応付け
└── index.ts  # queryModelGemini() └── usage.ts / types.ts
```

主な環境変数: `CLAUDE_CODE_USE_GEMINI=1`、`GEMINI_API_KEY`、`GEMINI_BASE_URL`（既定 `https://generativelanguage.googleapis.com/v1beta`）、`GEMINI_MODEL`、および階層別の `GEMINI_DEFAULT_SONNET_MODEL` / `GEMINI_DEFAULT_OPUS_MODEL`。

### 互換レイヤの制限

第三者カタログでは、いくつかの機能が使えません。

- **厳密なトークン計数がない** — 概算に戻るため、自動 compaction の発火時点がずれる
- **グローバルキャッシュが無い** — `shouldUseGlobalCacheScope()` が false を返し、`scope: 'org'` のみになる
- **一部の beta が使えない** — Anthropic 固有の beta ヘッダに依存するもの
- **Claude モデルカタログ行が出ない** — `# Environment` が `claude-*` の id を渡さない

設定の真の出典は `docs/zh/features/providers.md` と `docs/zh/features/model-settings.md` を参照してください。

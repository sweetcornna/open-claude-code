# MCP プロトコル 2026-07-28 のサポート状況

## 1. 要約

occ の MCP **クライアント**と**サーバー**は、どちらも `@modelcontextprotocol` v2 SDK へ移行済みです。クライアントは 2026-08-02 以降、**デフォルトで version negotiation を開始**します。コンパイル時 feature flag の `MCP_2026` は `DEFAULT_BUILD_FEATURES` に追加済みです（それ以前は 1 リリースサイクルにわたって意図的に無効にし、本番トラフィックを移行前とバイト単位で一致させていました）。一方、サーバーはデフォルトで**両 era**をサポートし、クライアントが 2025 と 2026 のどちらで開始しても受け付けます。

このドキュメントでは、各部分の正確な状況、flag の意味、v1 SDK を廃止する順序を説明します。

## 2. 状況一覧

| capability | 状況 | `MCP_2026` の影響を受けるか |
|------|------|------------------|
| クライアント SDK | v2（`@modelcontextprotocol/client@2`） | いいえ。無条件に移行済み |
| version negotiation（`server/discover` probe） | **デフォルトで有効**（2026-08-02 以降） | **はい** |
| serve モード（`occ mcp serve`） | 両 era。デフォルトで双方を受け付ける | いいえ |
| computer-use MCP 子プロセス | 両 era。デフォルトで双方を受け付ける | いいえ |
| MRTR の複数ラウンドツール呼び出し | 接続の era に応じて自動的に有効になる | 間接的（先に modern へ negotiation する必要がある） |
| outputSchema の検証 + degradation | **デフォルトビルドで有効** | いいえ |
| OAuth hardening（RFC 9207 など） | **デフォルトビルドで有効** | いいえ |
| sampling/createMessage | 実装済み。`OCC_MCP_SAMPLING=1` で opt-in（§6.5 を参照） | いいえ |

要点: 表のうち `MCP_2026` が制御するのは 1 行だけです。それ以外は era に依存しない動作か、build flag ではなく**接続が実際に negotiation した era**によって決まります。

## 3. `MCP_2026` flag の意味

### 3.1 デフォルトで有効（2026-08-02 以降）

`scripts/defines.ts` の `DEFAULT_BUILD_FEATURES` には `'MCP_2026'` が含まれ、dev モードと build 成果物の両方でデフォルト有効です。それ以前は「バイト単位で不変」の段階的導入期間として、この行を 1 リリースサイクルにわたり意図的にコメントアウトしていました。

### 3.2 ロールバック方法

完全にロールバックするには、`scripts/defines.ts` の該当行を再びコメントアウトします。この flag は永続状態を持たず、設定にもディスクにも書き込みません。リポジトリ全体で唯一のゲートは `clientFactory.ts` にあります。`bun test` では `feature()` が引き続きコンパイル時の `false` になる点に注意してください（テスト自身が `bun:bundle` を mock します）。negotiation matrix test は両 era をカバーしています。

### 3.3 有効にすると何が変わるか

**変わるのは 1 点だけです。`connect()` の開始方法です。**

- 無効: SDK に `versionNegotiation` を渡さない。SDK は「未指定」を `mode: 'legacy'` と解釈し、2025 の `initialize` handshake を使う。wire traffic は移行前の v1 クライアントとバイト単位で同一になる
- 有効: `{ mode: 'auto' }` を渡す。`connect()` は最初に `server/discover` probe を送り、**明確な modern の証拠**が得られた場合だけ 2026-07-28 を選び、それ以外は `initialize` へフォールバックする

コスト（有効化前に把握すべき点）:

- connect ごとに 1 round trip が増える
- SDK 組み込みの stdio transport では、**短命な子プロセス**が 1 つ増える。probe は使い捨ての sibling process で実行します。これにより、未知の pre-`initialize` リクエストを受けると終了する古いサーバーも legacy サーバーと判定されるだけで、本接続には影響しません

## 4. version negotiation と「era」

### 4.1 唯一の構築箇所

`src/services/mcp/clientFactory.ts` は、クライアント経路上で `new Client(...)` を実行する**唯一**の場所です。negotiation の方式はここで一度だけ決まり、下流はすべて era に依存しません。

```ts
createMcpClient()                      // この build のデフォルト方式を使う
createMcpClient({ versionNegotiation }) // 上書き（テスト用の seam）
```

`feature()` はコンパイル時に評価され、`bun test` では常に `false` なので、**テストから flag が選択する経路へ到達することはありません**。`versionNegotiation` パラメータは、このために用意したテスト seam です。`{ mode: 'auto' }` または `{ mode: { pin: MCP_MODERN_PROTOCOL_VERSION } }` を渡すと、flag が有効な場合と同じコードを実行できます。

### 4.2 era は「接続」の属性であり、「build」の属性ではない

最も誤解しやすい点です。

> `MCP_2026` を組み込んだクライアントでも、2025 サーバーへ接続すれば**そのまま** `'legacy'` になります。

したがって、動作を分岐するときは接続を調べる必要があり、flag をもう一度判定してはいけません。

```ts
mcpProtocolEra(client)   // 'legacy' | 'modern' | undefined（未接続）
isModernMcpEra(client)   // === 'modern'
```

### 4.3 2026-07-28 へ入る経路は probe だけ

`MCP_MODERN_PROTOCOL_VERSION = '2026-07-28'` は、意図的に `SUPPORTED_PROTOCOL_VERSIONS` と `initialize` の version list から除外されています。つまり、legacy handshake が modern を negotiation することは決してありません。2026 へ入る唯一の経路は `server/discover` です。

## 5. serve モード（両 era）

`serveStdio()` は次の 2 箇所で使います。

| エントリ | ファイル |
|------|------|
| `occ mcp serve`（occ の組み込みツールを公開） | `src/entrypoints/mcp.ts` |
| `occ --computer-use-mcp` 子プロセス | `src/utils/computerUse/mcpServer.ts` |

どちらもデフォルトの `legacy: 'serve'` を使います。2025 の開始メッセージ（`initialize`、または宣言のない任意のメッセージ）は、同じファクトリが生成した 2025 インスタンスに固定され、手動で接続した stdio server と同じ動作になります。2026 の開始メッセージは modern へ進みます。**handler 本体は era に依存せず**、同じ `setRequestHandler` 群が両 era に応答します。

直感的ではありませんが重要な実装制約が 2 つあります。どちらもコードのコメントに記載済みなので、「最適化」で削除しないでください。

1. ファクトリは**呼び出しごとに新しいインスタンスを作る**アロー関数でなければならず、1 つのインスタンスを capture して再利用してはいけません。`serveStdio` は「`server/discover` で始まった後に 2025 のメッセージが続く」場合、`discardProbeInstance()` の後に `connectInstance('legacy')` を実行し、ファクトリを**2 回呼び出します**。インスタンスを再利用すると、そのインスタンス自身が `close()` された後に再接続することになります
2. `serveStdio(...)` に `await` は不要です。内部で `wire.start()` を同期的に呼び出し、rejection を `onerror` へルーティングします。stdin listener は通常どおり登録され、プロセスも通常どおり存続します。これは従来の `await server.connect(transport)` と同じ動作です

`MCP_2026` は serve 側を**制御しません**。flag が制御するのはクライアントが probe するかどうかであり、サーバーが応答するかどうかではありません。将来、組み込みサーバーを modern 専用にするなら、`legacy: 'reject'` へ変更します。

## 6. MRTR（複数ラウンドツール呼び出し）

### 6.1 modern era の elicitation はサーバーリクエストではなくなった

2026-07-28 には、`elicitation/create` という server→client リクエストチャネルが**存在しません**。サーバーは `tools/call` へ `input_required` 結果を返し、その結果へ elicitation を埋め込みます。SDK の autofill driver がそれをクライアント登録済みの handler へ dispatch し、その呼び出しを最大 `inputRequired.maxRounds`（デフォルト 10）ラウンドまで再試行します。

opaque な `requestState` は driver 自身がバイト単位で echo し、**host code は関与せず、本番環境へ送る内容に影響してはなりません**。

### 6.2 ラウンド番号は `onprogress` からしか取得できない

handler に渡される driver のコンテキストにはラウンド番号がありません。合成コンテキストの `id` は `inputRequests` の key であり、関連付けだけに使われ、各ラウンドで同じ値になります。クライアント側では `requestState` accessor が常に空です。ラウンド番号を伝える唯一のチャネルは、**呼び出し元の `onprogress`** です。driver は各ラウンドの開始時にこれを**直接呼び出し**（progress notification は送信しない）、そのラウンドのリクエストを dispatch する**前**に実行します。この順序により、elicitation handler 内の `currentMrtrRound()` は正しい値を取得できます。

`src/services/mcp/mrtrRounds.ts` は `Client` を key とする `WeakMap` にラウンド番号を記録します。UI は第 2 ラウンド以降、ダイアログのタイトルに `(round N)` を表示します（第 1 ラウンドは 1 回限りの elicitation と区別できないため表示しません）。REPL はラウンド番号をダイアログの React key に組み込みます。これにより、2 ラウンドが同じ requestId を共有しても、前ラウンドの回答を持つフォームが再利用されません。

**表示専用です。** ラウンド番号が誤っていても失われても、ダイアログの 1 行の装飾に影響するだけで、wire へ送信されることはありません。

### 6.3 既知のトレードオフと未実装部分

- **SDK 文字列への依存（意図的）**: driver 自身の progress 文言 `Fulfilling input required by '<method>' (round N)` を照合してラウンド番号を復元します。SDK は構造化フィールドを一切公開していないためです。SDK upgrade で文言が変わった場合は、カウントを黙って失うのではなく、`negotiationMatrix.test.ts` のラウンド関連の 2 ケースが**失敗します**。これは意図した failure mode です
- **`mrtrProgressCallback` を「常に callback を返す」ように単純化しない**: SDK は `onprogress` が設定されている場合だけ、リクエストに `_meta.progressToken` を付けます。tracker を無条件に設定すると、occ は**すべての** 2025 サーバーに対する全ツール呼び出しで progress token を通知し始めます。専用の legacy ケースがこの動作を防いでいます
- **並行呼び出しはカウンターを共有する**: ラウンド番号は Client 単位で記録するため、同じ接続で 2 つの MRTR 呼び出しを並行実行するとカウンターを共有し、互いに誤った番号を付ける可能性があります。影響は表示とフォーム identity だけです。正しく修正するには SDK が per-call の関連付けを公開する必要がありますが、現在はありません
- **`SdkErrorCode.InputRequiredRoundsExceeded` は degradation 対応済み**（commit `00c2db80`）: `maxRounds` を超えた呼び出しでは、`callTool` から生の `SdkError` を投げなくなりました。`src/services/mcp/inputRequiredDegradation.ts` の `inputRequiredRoundsExceededDegradation()` が schema 違反と同様にテキスト結果へ degradation し、`data.lastResult` に最後の `{inputRequests, requestState?}` を含めるため、turn は継続できます。接続箇所は `client.ts` の `callMCPTool` です

legacy era の `-32042` elicitation loop は影響を受けず、そのまま維持されています。

## 6.5 sampling/createMessage（2026-08-02 に追加）

`src/services/mcp/samplingHandler.ts`。**デフォルトで無効**です。`OCC_MCP_SAMPLING=1` の場合だけ、サーバーへ
`sampling` capability を advertise して handler を登録します。応答する予定がないなら、サーバーへ sampling を要求するよう促しません。

- リクエストは `sideQuery()` から小型/高速モデル（`getSmallFastModel()`）へ送られ、セッションの provider に従って自動的にルーティングされる
  （Anthropic / OpenAI 互換 / Gemini / Grok のすべてを利用可能）
- hard limit: リクエストごとの `maxTokens` を 4096 に clamp する。セッションごとに最大 100 回の sampling 呼び出し（サーバー間でカウントを共有）
  仕様では人間を loop 内に保つよう定めている。リクエスト単位の承認 UI が完成するまでは、明示的な opt-in と上限がその loop になる
- v1 の範囲: テキストのみ（image content block はスキップ）。`CreateMessageResultWithTools`
  （augmented tool calls）は返さない。sampling 結果にツール呼び出しが含まれないことは仕様で許可されている
- stop_reason のマッピング: `max_tokens`→`maxTokens`、`stop_sequence`→`stopSequence`、その他→`endTurn`

## 7. outputSchema の検証と degradation

### 7.1 デフォルトビルドに影響する

両世代の SDK は、ツールが**advertise した** `outputSchema` を使ってサーバーが実際に返した結果を検証し、一致しなければ**例外を投げます**。この判断が示すのはサーバーの自己記述に問題があることであり、ツールが動作しなかったことではありません。`outputSchema` を宣言しながらプレーンテキストを返すサーバーには装飾的な bug があるだけです。それを理由にツール呼び出し全体を失敗させると、小さな bug が壊れた turn に変わります。

そのため、`callMCPTool` はこの種の例外を分類し、**テキスト結果へ degradation** します。モデルは引き続き結果を参照でき、turn も継続します。同時に debug ログと `tengu_mcp_output_schema_degraded` analytics event を記録します。

**検証は response cache によって「作動状態」になります**。validator は cache 済みの `tools/list` 集約結果からコンパイルされますが、この cache へ書き込むのは `listTools()` だけです。生の `request({ method: 'tools/list' })` では validator が空のまま動作します。occ の検出経路は `listTools()` を使うため、これは safety net ではなく**実際に通る経路**です。（なお、`listTools()` は pagination も行いますが、生の request は行いません。）

動作の変化: 規則に従わないサーバーは「黙って通る」状態から「記録 + degradation」へ変わりました。**この動作は era に依存しないため、デフォルトビルドへ影響します**。

### 7.2 4 種類の分類

`src/services/mcp/outputSchemaDegradation.ts` の `outputSchemaViolation()` は次を返します。

| 値 | 意味 |
|----|------|
| `missing_structured_content` | schema を宣言したが構造化内容を返さなかった。実環境で最も多い |
| `schema_mismatch` | 構造化内容を返したが検証に通らなかった |
| `validator_failed` | validator 自体が例外を投げた |
| `invalid_output_schema` | 宣言された schema をコンパイルできず、リクエストも送信されなかった |

SDK は 4 種類すべてを、message テキストだけで区別できる `ProtocolError` として報告します。そのため、利用可能な分類手段はテキスト照合だけです。分類の失敗は黙って無視しません。未分類の違反は汎用エラー処理へ進み、接続前と同様に呼び出しが失敗します。テストで実際の違反に実際の validator を実行させるのはこのためです。

### 7.3 `packages/mcp-client` では意図的に作動させていない

`packages/mcp-client/src/discovery.ts` は、**意図的に**引き続き `request({ method: 'tools/list' })` を使います。これは並行して存在する、現在は**未接続**の実装です（`src/` では `discoverTools`/`callMcpTool` を import している箇所がありません）。その sibling である `execution.ts` には degradation の safety net がありません。ここで validator を作動させると、host 側で degradation しているサーバー群が hard failure になります。「一貫性」のために統一せず、先に degradation の safety net を移植してください。

## 8. OAuth hardening

この部分は `feature('MCP_2026')` の後ろに置かず、すべてのユーザーに無条件で適用します。修正するのは現在すでに存在する mix-up / multi-tenant の認証情報混同問題です。セキュリティ修正をデフォルト無効の flag に隠せば、誰にも届きません。

| 項目 | 説明 |
|----|------|
| RFC 9207 `iss` の検証 | loopback callback と貼り付けた callback URL の両経路で、`code`/`state`/`error*` を読む**前**に `iss` を検証する（mix-up 攻撃では、これらはすべて攻撃者が制御可能）。§2.4 の判定表は v2 SDK の `validateAuthorizationResponseIssuer` に委譲する。重複する `iss` は直ちに拒否する（各 query parser で「どの重複値を優先するか」が異なるため）。`issuer_mismatch` telemetry reason を追加。ブラウザ向けの 400 ページでは、受信した issuer を**意図的に表示しない** |
| issuer ごとの認証情報スロット | スロットを `${serverName}\|${sha256(config)}` から `${baseKey}\|iss:${sha256(issuer)}` へ変更する。base key は引き続き接頭辞なので、追加の索引なしで 1 台のサーバーの全スロットを列挙できる。比較では末尾のスラッシュ 1 つを許容し（SDK の `issuersMatch` と一致させる）、同じ issuer の表記違いが 2 スロットへ分裂するのを防ぐ |
| 移行 | 後方互換性を維持する。**別の** issuer が明記されたエントリは奪わず、その issuer 自身の配下へ再分類する。**所有者不明**のエントリ（upgrade 前のすべてのインストール）は、最初に検出した issuer へ割り当てる。所属を証明する情報はなく、移行を拒否すれば既存ユーザー全員がログアウトする。誤った推測のコストは 1 回の 401（これらのユーザーが元から遭遇するもの）であり、その後の検出フローが実際の issuer を示すため、次回の解析では正確になる |
| `application_type: 'native'` | DCR 登録リクエストで明示的に宣言する（RFC 8252 §8.3 / SEP-837）。occ は loopback へ redirect するため、OIDC デフォルトの `web` とは矛盾し、一部のサーバーはそのまま拒否する |

macOS keychain では 1 エントリに 4096 byte の上限がある点に注意してください。置き換えられた base エントリは merge せず**破棄**します。同じ理由で、「認証を消去」はそのサーバーの全 issuer スロットを消去するようになりました。

## 9. SDK バージョンの現状と v1 の廃止順序

### 9.1 3 package が同時に依存ツリーにある

`package.json` では現在、3 つすべてが必要です。

```jsonc
"@modelcontextprotocol/client": "^2.0.0",  // クライアント。全面的に使用済み
"@modelcontextprotocol/server": "^2.0.0",  // サーバー。全面的に使用済み
"@modelcontextprotocol/sdk":    "^1.29.0"  // v1。まだ削除できない。以下を参照
```

### 9.2 v1 をまだ削除できない理由

残存箇所を 2 種類に分けます。**型 import**（`import type`。build 時に消去され、`tsc` だけが必要）と**値 import**（実際に成果物へ入るもの）です。

**値 import（production code。v1 の実際の runtime dependency）:**

| ファイル | 使用する v1 の値 |
|------|-----------|
| `src/services/mcp/auth.ts` | `auth`、`refreshAuthorization`、`discoverAuthorizationServerMetadata`、`discoverOAuthServerInfo`、5 個の OAuth error class、`OAuthTokensSchema` など |
| `src/services/mcp/xaa.ts` | `discoverAuthorizationServerMetadata`、`discoverOAuthProtectedResourceMetadata` |
| `src/services/mcp/xaaIdpLogin.ts` | `startAuthorization`、`exchangeAuthorization`、`OpenIdProviderDiscoveryMetadataSchema` |
| `src/utils/mcpWebSocketTransport.ts` | `JSONRPCMessageSchema` |

**型 import のみ（`implements LegacyTransport` による両 era の証明。最後に変更する）:**

- `src/services/mcp/InProcessTransport.ts`
- `src/services/mcp/SdkControlTransport.ts`
- `packages/mcp-client/src/transport/InProcessTransport.ts`
- `src/utils/mcpWebSocketTransport.ts`（上記の値 import も存在）

これらの class にある `implements LegacyTransport, ModernTransport` は**意図的**です。これにより、in-process computer-use 経路は同じ transport を v2 `Server` へ渡せます。v1 側を外すと、反対側に残る v1 consumer が中断します。

**テスト（両 era の証明）:** `src/services/mcp/__tests__/negotiationMatrix.test.ts`（v1 `Server` + request schema）、`src/entrypoints/__tests__/mcp.test.ts`（v1 `Client` が occ の両 era serve を呼ぶ）。この 2 つは実際の v1 peer を使い、「実際に 2025 へサービスを提供できる」ことを証明します。両 era をサポートすると宣言する限り、残す必要があります。

### 9.3 廃止順序

1. **OAuth を v2 へ移行する**（`auth.ts` / `xaa.ts` / `xaaIdpLogin.ts`）。v2 の root は対応するものを export しています。`auth`、`startAuthorization`、`exchangeAuthorization`、`refreshAuthorization`、`registerClient`、`discoverAuthorizationServerMetadata` などです。**型の変化が 1 箇所あります**。v1 で個別 subclass だった各 error（`InvalidGrantError`、`ServerError`、`TemporarilyUnavailableError`、`TooManyRequestsError`）は、v2 では単一の `OAuthError` と、判別用の `OAuthErrorCode` enum に統合されるため、`instanceof` の分岐を書き換える必要があります。移行後は 2 つの workaround も削除できます。`clientMetadata` の戻り値型に付けた `& { application_type?: string }` intersection（v1 型にはこのフィールドがなく、v2 にはある）と、`issuerBaselineFromMetadata` の `unknown` 引数（`authorization_response_iss_parameter_supported` は v1 型にないが parse は通る）です
2. **WebSocket transport の parser を置き換える**: `JSONRPCMessageSchema.parse(x)` → v2 の `parseJSONRPCMessage(x)`（signature は `(value: unknown) => JSONRPCMessage`）。parse failure で投げる error type も変わるため、変更時にはエラー処理も確認する
3. 1+2 が完了すると、production code には型 import だけが残る。その時点で `@modelcontextprotocol/sdk` を `dependencies` から **`devDependencies` へ降格**できる。成果物では不要になり、`tsc` と両 era のテストでは引き続き利用できる。完全削除を待つ必要がない、有用な中間状態である
4. **最後**に両 era のテストと transport の `implements LegacyTransport` 宣言を変更する。削除は「2025 クライアントへサービスを提供できる」という約束の放棄に等しく、依存関係整理の副作用ではなく、独立した意図的な製品判断にする必要がある

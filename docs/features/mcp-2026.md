# MCP 协议 2026-07-28 支持现状

## 1. 一句话总结

occ 的 MCP **客户端**和**服务端**都已迁到 `@modelcontextprotocol` v2 SDK，且客户端自 2026-08-02 起**默认开口协商** —— 编译期 feature flag `MCP_2026` 已进 `DEFAULT_BUILD_FEATURES`（此前刻意关闭一个发布周期，线上流量与迁移前逐字节一致）。服务端则默认**双时代**：无论客户端用 2025 还是 2026 开场都能接。

这份文档说明每一块的确切状态、开关语义，以及 v1 SDK 的退役顺序。

## 2. 状态总览

| 能力 | 状态 | 受 `MCP_2026` 影响？ |
|------|------|------------------|
| 客户端 SDK | v2（`@modelcontextprotocol/client@2`） | 否，已无条件迁移 |
| 版本协商（`server/discover` 探测） | **默认开**（2026-08-02 起） | **是** |
| serve 模式（`occ mcp serve`） | 双时代，默认两边都接 | 否 |
| computer-use MCP 子进程 | 双时代，默认两边都接 | 否 |
| MRTR 多轮工具调用 | 随连接时代自动生效 | 间接（要先协商上 modern） |
| outputSchema 校验 + 降级 | **已生效于默认构建** | 否 |
| OAuth 加固（RFC 9207 等） | **已生效于默认构建** | 否 |
| sampling/createMessage | 已实现，`OCC_MCP_SAMPLING=1` opt-in（见 §6.5） | 否 |

要点：表里只有一行是 `MCP_2026` 控制的。其余要么是时代无关的行为，要么由**连接实际协商到的时代**决定，而不是由构建标志决定。

## 3. `MCP_2026` 标志语义

### 3.1 默认开启（2026-08-02 起）

`scripts/defines.ts` 的 `DEFAULT_BUILD_FEATURES` 里包含 `'MCP_2026'`，dev 模式与 build 产物默认带上。此前该行刻意注释掉一个发布周期，作为"逐字节不变"的灰度期。

### 3.2 回滚方式

把 `scripts/defines.ts` 里那行重新注释掉就是完整回滚 —— 这个标志没有任何持久化状态，不写配置、不写磁盘，全仓唯一门控点在 `clientFactory.ts`。注意 `bun test` 下 `feature()` 仍是编译期 `false`（测试自行 mock `bun:bundle`），协商矩阵测试对两个时代都有覆盖。

### 3.3 打开后到底变了什么

**只变一件事：`connect()` 的开场白。**

- 关：不向 SDK 传 `versionNegotiation`。SDK 把"没说"读作 `mode: 'legacy'`，走 2025 的 `initialize` 握手，线路流量与迁移前的 v1 客户端逐字节相同。
- 开：传 `{ mode: 'auto' }`。`connect()` 先发 `server/discover` 探测，只有拿到**明确的 modern 证据**才落到 2026-07-28，否则回退 `initialize`。

代价（打开前要知道）：

- 每次 connect 多一个来回。
- 在 SDK 自带的 stdio transport 上，多一个**短命子进程** —— 探测跑在一个用完即弃的兄弟进程上，这样"遇到未知的 pre-`initialize` 请求就自杀"的老服务器仍然只被判定为 legacy 服务器，而不会连累真正的连接。

## 4. 版本协商与"时代"

### 4.1 唯一构造点

`src/services/mcp/clientFactory.ts` 是客户端路径上**唯一**的 `new Client(...)`。协商姿势只在这里决定一次，下游全部时代无关。

```ts
createMcpClient()                      // 走本构建的默认姿势
createMcpClient({ versionNegotiation }) // 覆盖（测试用的接缝）
```

`feature()` 是编译期求值、在 `bun test` 下恒为 `false`，所以**测试永远走不到标志选中的那条路**。`versionNegotiation` 参数就是为此存在的测试接缝：传 `{ mode: 'auto' }` 或 `{ mode: { pin: MCP_MODERN_PROTOCOL_VERSION } }` 能跑到标志打开时的同一段代码。

### 4.2 时代是"连接"的属性，不是"构建"的属性

这是最容易搞错的一点：

> 一个编译进了 `MCP_2026` 的客户端，连上 2025 服务器时**照样**落在 `'legacy'`。

所以任何行为差异都必须问连接、而不是再判一次标志：

```ts
mcpProtocolEra(client)   // 'legacy' | 'modern' | undefined（未连接）
isModernMcpEra(client)   // === 'modern'
```

### 4.3 2026-07-28 只能从探测进

`MCP_MODERN_PROTOCOL_VERSION = '2026-07-28'` 被**刻意**排除在 `SUPPORTED_PROTOCOL_VERSIONS` 和 `initialize` 的版本列表之外。也就是说 legacy 握手在任何情况下都不可能协商到 modern —— 走进 2026 的唯一门是 `server/discover`。

## 5. serve 模式（双时代）

`serveStdio()` 同时用于两个地方：

| 入口 | 文件 |
|------|------|
| `occ mcp serve`（暴露 occ 内置工具） | `src/entrypoints/mcp.ts` |
| `occ --computer-use-mcp` 子进程 | `src/utils/computerUse/mcpServer.ts` |

两者都用默认的 `legacy: 'serve'`：2025 开场（`initialize`，或任何无声明的消息）会被钉到一个同工厂产出的 2025 实例上，和手工接线的 stdio server 行为一致；2026 开场则走 modern。**处理器本体是时代无关的**，同一批 `setRequestHandler` 服务两个时代。

两个非显然但重要的实现约束（都已在代码注释里，别"优化"掉）：

1. 工厂必须是**每次调用新建实例**的箭头函数，不能捕获一个实例复用。`serveStdio` 在"`server/discover` 开场后跟一条 2025 消息"的情况下会 `discardProbeInstance()` 再 `connectInstance('legacy')`，**二次调用工厂**；复用实例等于在它自己 `close()` 之后又把它接上。
2. `serveStdio(...)` 不需要 `await`。它内部同步调用 `wire.start()` 并把 rejection 路由到 `onerror`，stdin 监听器照常挂上，进程照常存活 —— 与旧的 `await server.connect(transport)` 行为等价。

`MCP_2026` **不控制** serve 端。标志管的是客户端要不要探测，不管服务端愿不愿意回答。若将来想让内置服务端只服务 modern，改 `legacy: 'reject'`。

## 6. MRTR（多轮工具调用）

### 6.1 modern era 的 elicitation 不再是服务端请求

2026-07-28 里 `elicitation/create` 这条 server→client 请求通道**不存在**了。服务器改为用 `input_required` 结果回答 `tools/call`，把 elicitation 嵌在结果里；SDK 的自动填充驱动把它派发给客户端注册的处理器，然后重试该调用，最多 `inputRequired.maxRounds`（默认 10）轮。

不透明的 `requestState` 由驱动自己逐字节回显，**宿主代码不参与、也永远不得影响上线的内容**。

### 6.2 轮次只能从 `onprogress` 拿

驱动交给处理器的上下文里没有轮次：合成上下文的 `id` 是 `inputRequests` 的 key（只用于关联，每轮重复），`requestState` 访问器在客户端侧恒为空。唯一报告轮次的通道是**发起调用的 `onprogress`** —— 驱动在每轮开头**直接调用**它（不是发进度通知），且在派发该轮请求**之前**。这个顺序正是 `currentMrtrRound()` 能在 elicitation 处理器里读到正确值的原因。

`src/services/mcp/mrtrRounds.ts` 用一个以 `Client` 为键的 `WeakMap` 记录轮次；UI 从第 2 轮起在对话框标题上显示 `(round N)`（第 1 轮与一次性 elicitation 无法区分，故不显示），REPL 把轮次折进对话框的 React key，避免两轮共用一个重复的 requestId 时复用到上一轮答案的表单。

**纯展示。** 轮次错了或丢了只影响一行对话框装饰，永远不上线路。

### 6.3 已知取舍与未做的部分

- **SDK 字符串依赖（有意为之）**：轮次靠匹配驱动自己的进度文案 `Fulfilling input required by '<method>' (round N)` 还原 —— SDK 没有任何结构化字段暴露它。SDK 升级改了措辞会让 `negotiationMatrix.test.ts` 里两个轮次相关用例**失败**，而不是悄悄丢掉计数。这是设计好的失败模式。
- **不要把 `mrtrProgressCallback` 简化成"总是返回回调"**：SDK 只在设置了 `onprogress` 时才给请求挂 `_meta.progressToken`。无条件的 tracker 会让 occ 对**每一个** 2025 服务器的每一次工具调用都开始广告 progress token。有专门的 legacy 用例守着这条。
- **并发调用共享计数器**：轮次按 Client 记，同一连接上两个并发的 MRTR 调用会共用一个计数器、可能互相标错。仅影响展示与表单身份。要真正修好需要 SDK 暴露 per-call 关联，目前没有。
- **`SdkErrorCode.InputRequiredRoundsExceeded` 已降级处理**（commit `00c2db80`）：超过 `maxRounds` 的调用不再从 `callTool` 抛原始 `SdkError`，而是由 `src/services/mcp/inputRequiredDegradation.ts` 的 `inputRequiredRoundsExceededDegradation()` 像 schema 违规那样降级成文本结果（携带 `data.lastResult` 里最后一份 `{inputRequests, requestState?}`），turn 得以存活。接线点在 `client.ts` 的 `callMCPTool`。

legacy era 的 `-32042` elicitation 循环未受影响，原样保留。

## 6.5 sampling/createMessage（2026-08-02 新增）

`src/services/mcp/samplingHandler.ts`。**默认关闭**：只有 `OCC_MCP_SAMPLING=1` 时才向服务器
advertise `sampling` capability 并注册处理器 —— 不打算响应就不邀请服务器来采样。

- 请求经 `sideQuery()` 走小/快模型（`getSmallFastModel()`），自动随会话的 provider 路由
  （Anthropic / OpenAI 兼容 / Gemini / Grok 都能用）。
- 硬上限：单请求 `maxTokens` clamp 到 4096；每会话最多 100 次采样调用（跨服务器共享计数）。
  规范说人应留在环内 —— 在做出逐请求审批 UI 之前，环就是这个显式 opt-in + 上限。
- v1 范围：纯文本（image 内容块跳过）；不返回 `CreateMessageResultWithTools`
  （augmented tool calls）—— 采样结果不含工具调用是规范允许的。
- stop_reason 映射：`max_tokens`→`maxTokens`、`stop_sequence`→`stopSequence`、其余→`endTurn`。

## 7. outputSchema 校验与降级

### 7.1 这一块影响默认构建

两代 SDK 都会拿工具**广告的** `outputSchema` 去校验服务器实际返回的结果，不匹配就**抛异常**。这个判决说的是服务器的自我描述有问题，不是工具没干活：一个声明了 `outputSchema` 却回纯文本的服务器只是有个装饰性 bug，为它让整个工具调用失败等于把小 bug 变成坏掉的 turn。

`callMCPTool` 因此对这类异常分类并**降级为文本结果**，模型仍能看到结果、turn 得以存活，同时打一条 debug 日志和 `tengu_mcp_output_schema_degraded` 分析事件。

**校验是被 response cache "上膛"的**：校验器从缓存的 `tools/list` 聚合结果编译而来，而只有 `listTools()` 会写这个缓存 —— 裸的 `request({ method: 'tools/list' })` 会让它保持空转。occ 的发现路径用 `listTools()`，所以这是一条**活路径**而不是安全网。（顺带：`listTools()` 还会走分页，裸请求不会。）

行为变化：不守规矩的服务器从"静默通过"变成"记录 + 降级"。**这一条与时代无关，所以它移动的是默认构建**。

### 7.2 四种分类

`src/services/mcp/outputSchemaDegradation.ts` 的 `outputSchemaViolation()` 返回：

| 值 | 含义 |
|----|------|
| `missing_structured_content` | 声明了 schema 却没返回结构化内容。野外最常见 |
| `schema_mismatch` | 返回了结构化内容但校验不过 |
| `validator_failed` | 校验器本身抛了 |
| `invalid_output_schema` | 声明的 schema 根本编译不了，请求发都没发出去 |

SDK 把四种情况都报成仅靠 message 文本区分的 `ProtocolError`，所以匹配文本是唯一可用的分类手段。分类失败不是静默的：未分类的违规会落到通用错误处理、像接线之前那样让调用失败 —— 这正是测试要用真实违规驱动真实校验器的原因。

### 7.3 `packages/mcp-client` 有意没有上膛

`packages/mcp-client/src/discovery.ts` **刻意**仍用 `request({ method: 'tools/list' })`。它是一份平行的、目前**未接线**的实现（`src/` 里没有任何地方 import 它的 `discoverTools`/`callMcpTool`），而它的兄弟 `execution.ts` 没有降级网。给它上膛会硬失败掉宿主这边正在降级的那批服务器。不要为了"一致性"统一，先把降级网移植过去。

## 8. OAuth 加固

这一块**没有**放在 `feature('MCP_2026')` 后面，对所有用户无条件生效 —— 它们修的是今天就存在的 mix-up / 多租户串号问题，把安全修复藏在默认关闭的标志后面等于没人拿到。

| 项 | 说明 |
|----|------|
| RFC 9207 `iss` 校验 | loopback 回调和粘贴回调 URL 两条路径都在读 `code`/`state`/`error*` **之前**校验 `iss`（mix-up 攻击下这些全是攻击者可控的）。§2.4 判定表委托给 v2 SDK 的 `validateAuthorizationResponseIssuer`。重复的 `iss` 直接拒绝（各家 query 解析器对"哪个重复值胜出"意见不一）。新增 `issuer_mismatch` 遥测原因。面向浏览器的 400 页**故意不回显**收到的 issuer |
| 凭据按 issuer 分槽 | 槽位从 `${serverName}\|${sha256(config)}` 变为 `${baseKey}\|iss:${sha256(issuer)}`。base key 仍是前缀，所以一台服务器的所有槽位无需额外索引即可枚举。比较容忍一个结尾斜杠（对齐 SDK 的 `issuersMatch`），否则同一 issuer 的两种写法会裂成两个槽 |
| 迁移 | 向后兼容：写明了**别的** issuer 的条目会被重新归到它自己的 issuer 名下，而不是被抢走；**无归属**条目（所有升级前的安装）归第一个被发现的 issuer。没有证据可归属，而拒绝迁移等于把每个现存用户登出；猜错的代价是一次 401（正是这些用户本来就会遇到的），之后发现流程会给出真正的 issuer，下一次解析就精确了 |
| `application_type: 'native'` | DCR 注册请求显式声明（RFC 8252 §8.3 / SEP-837）。occ 重定向到 loopback，OIDC 默认的 `web` 自相矛盾，部分服务器会直接拒 |

注意 macOS keychain 单条 4096 字节上限：被取代的 base 条目是**丢弃**而不是合并的，同一原因下"清除认证"现在会抹掉该服务器的所有 issuer 槽位。

## 9. SDK 版本现状与 v1 退役顺序

### 9.1 三个包同时在树里

`package.json` 目前三个都需要：

```jsonc
"@modelcontextprotocol/client": "^2.0.0",  // 客户端，已全面使用
"@modelcontextprotocol/server": "^2.0.0",  // 服务端，已全面使用
"@modelcontextprotocol/sdk":    "^1.29.0"  // v1，尚不能删，见下
```

### 9.2 为什么 v1 还删不掉

区分两类残留 —— **类型导入**（`import type`，构建时擦除，只有 `tsc` 需要）和**值导入**（真的进产物）。

**值导入（生产代码，v1 的真实运行时依赖）：**

| 文件 | 用到的 v1 值 |
|------|-----------|
| `src/services/mcp/auth.ts` | `auth`、`refreshAuthorization`、`discoverAuthorizationServerMetadata`、`discoverOAuthServerInfo`、5 个 OAuth 错误类、`OAuthTokensSchema` 等 |
| `src/services/mcp/xaa.ts` | `discoverAuthorizationServerMetadata`、`discoverOAuthProtectedResourceMetadata` |
| `src/services/mcp/xaaIdpLogin.ts` | `startAuthorization`、`exchangeAuthorization`、`OpenIdProviderDiscoveryMetadataSchema` |
| `src/utils/mcpWebSocketTransport.ts` | `JSONRPCMessageSchema` |

**仅类型导入（`implements LegacyTransport` 的双时代证明，最后才动）：**

- `src/services/mcp/InProcessTransport.ts`
- `src/services/mcp/SdkControlTransport.ts`
- `packages/mcp-client/src/transport/InProcessTransport.ts`
- `src/utils/mcpWebSocketTransport.ts`（同时还有上面那个值导入）

这些类里的 `implements LegacyTransport, ModernTransport` 是**故意**的：它正是让 in-process computer-use 路径把同一个 transport 喂给 v2 `Server` 的东西。拆掉 v1 那一半会打断仍在另一端的 v1 消费者。

**测试（双时代证明）：** `src/services/mcp/__tests__/negotiationMatrix.test.ts`（v1 `Server` + 请求 schema）、`src/entrypoints/__tests__/mcp.test.ts`（v1 `Client` 打 occ 的双时代 serve）。这两个用真 v1 对端证明"我们确实还能服务 2025"，只要还宣称双时代就应该留着。

### 9.3 退役顺序

1. **把 OAuth 搬到 v2**（`auth.ts` / `xaa.ts` / `xaaIdpLogin.ts`）。v2 根部导出了对应物：`auth`、`startAuthorization`、`exchangeAuthorization`、`refreshAuthorization`、`registerClient`、`discoverAuthorizationServerMetadata` 等。**注意一处形变**：v1 的每错误一个子类（`InvalidGrantError`、`ServerError`、`TemporarilyUnavailableError`、`TooManyRequestsError`）在 v2 里收敛成单个 `OAuthError` + `OAuthErrorCode` 枚举判别，需要改写 `instanceof` 分支。搬完还能顺手去掉两个 workaround：`clientMetadata` 返回类型上的 `& { application_type?: string }` 交集（v1 类型缺该字段，v2 有），以及 `issuerBaselineFromMetadata` 的 `unknown` 入参（`authorization_response_iss_parameter_supported` 在 v1 类型里缺失但能过解析）。
2. **换掉 WebSocket transport 的解析器**：`JSONRPCMessageSchema.parse(x)` → v2 的 `parseJSONRPCMessage(x)`（签名 `(value: unknown) => JSONRPCMessage`）。注意解析失败抛的错误类型会变，改的时候连它的错误处理一起看。
3. 做完 1+2，生产代码里就只剩类型导入了。此时 `@modelcontextprotocol/sdk` 可以从 `dependencies` **降级到 `devDependencies`** —— 产物不再需要它，`tsc` 和双时代测试仍然拿得到。这是一个有价值的中间态，不必等到彻底删除。
4. **最后**才是双时代测试与 transport 的 `implements LegacyTransport` 声明。删掉它们等于放弃"能服务 2025 客户端"这个承诺，应该是一个独立的、有意的产品决定，而不是依赖清理的副产品。

# MCP Protocol 2026-07-28 Support Status

## 1. Summary

Both the MCP **client** and **server** in occ have migrated to the `@modelcontextprotocol` v2 SDK, and the client has **negotiated by default** since 2026-08-02. The compile-time `MCP_2026` feature flag is now included in `DEFAULT_BUILD_FEATURES` (it was deliberately disabled for one release cycle so production wire traffic remained byte-for-byte identical to the pre-migration traffic). The server operates in **dual-era mode** by default: it accepts clients that begin with either the 2025 or 2026 protocol.

This document describes the exact status of each part, the semantics of the switch, and the retirement sequence for the v1 SDK.

## 2. Status overview

| Capability | Status | Affected by `MCP_2026`? |
|------|------|------------------|
| Client SDK | v2 (`@modelcontextprotocol/client@2`) | No; migration is unconditional |
| Version negotiation (`server/discover` probe) | **Enabled by default** (since 2026-08-02) | **Yes** |
| Serve mode (`occ mcp serve`) | Dual-era; accepts both by default | No |
| computer-use MCP subprocess | Dual-era; accepts both by default | No |
| MRTR multi-round tool calls | Activates automatically according to the connection era | Indirectly (the connection must first negotiate modern) |
| outputSchema validation and degradation | **Active in default builds** | No |
| OAuth hardening (RFC 9207, etc.) | **Active in default builds** | No |
| sampling/createMessage | Implemented; opt in with `OCC_MCP_SAMPLING=1` (see §6.5) | No |

The key point is that `MCP_2026` controls only one row in this table. Everything else is either era-independent behavior or depends on the **era actually negotiated by the connection**, not the build flag.

## 3. Semantics of the `MCP_2026` flag

### 3.1 Enabled by default since 2026-08-02

`DEFAULT_BUILD_FEATURES` in `scripts/defines.ts` includes `'MCP_2026'`, so development mode and build artifacts include it by default. The line was previously commented out deliberately for one release cycle as a byte-for-byte-stability canary period.

### 3.2 Rollback procedure

Commenting out that line in `scripts/defines.ts` again provides a complete rollback. The flag has no persistent state, writes no configuration, writes nothing to disk, and has exactly one gate in the repository: `clientFactory.ts`. Note that under `bun test`, `feature()` remains the compile-time value `false` (tests mock `bun:bundle` themselves); negotiation matrix tests cover both eras.

### 3.3 What enabling it changes

**It changes exactly one thing: the opening behavior of `connect()`.**

- Disabled: The client does not pass `versionNegotiation` to the SDK. The SDK interprets its absence as `mode: 'legacy'`, uses the 2025 `initialize` handshake, and produces wire traffic byte-for-byte identical to the pre-migration v1 client.
- Enabled: The client passes `{ mode: 'auto' }`. `connect()` first sends a `server/discover` probe and selects 2026-07-28 only when it receives **explicit modern evidence**; otherwise, it falls back to `initialize`.

Costs to understand before enabling it:

- Every connection requires one additional round trip.
- With the SDK's bundled stdio transport, each connection creates one additional **short-lived subprocess**. The probe runs in a disposable sibling process so that old servers that terminate on an unknown pre-`initialize` request are still classified as legacy servers without taking down the real connection.

## 4. Version negotiation and “eras”

### 4.1 The single construction point

`src/services/mcp/clientFactory.ts` is the **only** `new Client(...)` on the client path. It selects the negotiation strategy once; all downstream code is era-independent.

```ts
createMcpClient()                       // Use the default strategy for this build
createMcpClient({ versionNegotiation }) // Override it (test seam)
```

`feature()` is evaluated at compile time and is always `false` under `bun test`, so **tests can never reach the branch selected by the flag**. The `versionNegotiation` parameter exists as a test seam for this reason: passing `{ mode: 'auto' }` or `{ mode: { pin: MCP_MODERN_PROTOCOL_VERSION } }` exercises the same code that runs when the flag is enabled.

### 4.2 Era is a connection property, not a build property

This distinction is the easiest one to get wrong:

> A client compiled with `MCP_2026` still uses `'legacy'` when it connects to a 2025 server.

Therefore, behavior that differs by era must query the connection rather than check the flag again:

```ts
mcpProtocolEra(client)   // 'legacy' | 'modern' | undefined (not connected)
isModernMcpEra(client)   // === 'modern'
```

### 4.3 2026-07-28 is reachable only through probing

`MCP_MODERN_PROTOCOL_VERSION = '2026-07-28'` is **deliberately** excluded from `SUPPORTED_PROTOCOL_VERSIONS` and from the version list used by `initialize`. In other words, the legacy handshake can never negotiate modern under any circumstances. `server/discover` is the only route into the 2026 protocol.

## 5. Serve mode (dual-era)

`serveStdio()` is used in two places:

| Entry point | File |
|------|------|
| `occ mcp serve` (exposes occ's built-in tools) | `src/entrypoints/mcp.ts` |
| `occ --computer-use-mcp` subprocess | `src/utils/computerUse/mcpServer.ts` |

Both use the default `legacy: 'serve'`: a 2025 opening (`initialize`, or any message without a declaration) is pinned to a 2025 instance produced by the same factory, matching the behavior of the manually wired stdio server; a 2026 opening uses modern. **The handlers themselves are era-independent**: the same set of `setRequestHandler` registrations serves both eras.

Two non-obvious but important implementation constraints are documented in code and must not be “optimized” away:

1. The factory must be an arrow function that **constructs a new instance on every call**; it must not capture and reuse an instance. If `server/discover` is followed by a 2025 message, `serveStdio` calls `discardProbeInstance()` and then `connectInstance('legacy')`, which **invokes the factory a second time**. Reusing the instance would reconnect it after its own `close()`.
2. `serveStdio(...)` does not require `await`. It calls `wire.start()` synchronously and routes rejection to `onerror`; the stdin listeners remain attached and the process remains alive. This is equivalent to the previous `await server.connect(transport)` behavior.

`MCP_2026` **does not control** the serving side. The flag determines whether the client probes, not whether the server responds. If the built-in server should serve only modern clients in the future, change it to `legacy: 'reject'`.

## 6. MRTR (multi-round tool calls)

### 6.1 Elicitation is no longer a server request in the modern era

The server→client `elicitation/create` request channel **does not exist** in 2026-07-28. Instead, the server answers `tools/call` with an `input_required` result that embeds the elicitation. The SDK's automatic fulfillment driver dispatches it to the handler registered by the client and then retries the call, up to `inputRequired.maxRounds` rounds (10 by default).

The driver echoes the opaque `requestState` byte-for-byte by itself. **Host code does not participate and must never affect wire content.**

### 6.2 The round number is available only through `onprogress`

The context passed from the driver to the handler does not include a round number: the synthesized context `id` is the `inputRequests` key (used only for correlation and repeated on each round), while the `requestState` accessor is always empty on the client. The **calling invocation's `onprogress`** is the only channel that reports the round. At the start of each round, the driver **calls it directly** (rather than sending a progress notification), and it does so **before** dispatching that round's request. This order is precisely why `currentMrtrRound()` can read the correct value inside the elicitation handler.

`src/services/mcp/mrtrRounds.ts` records rounds in a `WeakMap` keyed by `Client`. Starting with round 2, the UI displays `(round N)` in the dialog title (round 1 is indistinguishable from one-shot elicitation, so it is not shown). The REPL folds the round into the dialog's React key, preventing the form from reusing the previous round's answer when two rounds share a repeated requestId.

**Presentation only.** A missing or incorrect round affects one line of dialog decoration and never reaches the wire.

### 6.3 Known trade-offs and omitted work

- **SDK string dependency (intentional)**: The round tracker reconstructs the round by matching the driver's own progress message, `Fulfilling input required by '<method>' (round N)`, because the SDK exposes no structured field for it. If an SDK upgrade changes that wording, the two round-related cases in `negotiationMatrix.test.ts` **fail** instead of silently losing the count. This is the intended failure mode.
- **Do not simplify `mrtrProgressCallback` to “always return a callback”**: The SDK adds `_meta.progressToken` to a request only when `onprogress` is set. An unconditional tracker would make occ advertise a progress token for **every tool call** to **every** 2025 server. A dedicated legacy test protects this constraint.
- **Concurrent calls share a counter**: Rounds are recorded per Client, so two concurrent MRTR calls on the same connection share one counter and can mislabel each other. This affects only presentation and form identity. Correct correlation requires a per-call identifier from the SDK, which is not currently available.
- **`SdkErrorCode.InputRequiredRoundsExceeded` is handled through degradation** (commit `00c2db80`): A call that exceeds `maxRounds` no longer throws the raw `SdkError` from `callTool`. Instead, `inputRequiredRoundsExceededDegradation()` in `src/services/mcp/inputRequiredDegradation.ts` degrades it into a text result, like a schema violation, carrying the final `{inputRequests, requestState?}` from `data.lastResult`. The turn remains alive. The integration point is `callMCPTool` in `client.ts`.

The legacy era's `-32042` elicitation loop is unchanged.

## 6.5 sampling/createMessage (added 2026-08-02)

`src/services/mcp/samplingHandler.ts`. **Disabled by default**: occ advertises the `sampling` capability and registers the handler only when `OCC_MCP_SAMPLING=1`. If occ does not intend to respond, it does not invite the server to sample.

- Requests go through `sideQuery()` to the small/fast model (`getSmallFastModel()`) and automatically follow the session's provider routing
  (Anthropic / OpenAI-compatible / Gemini / Grok are all supported).
- Hard limits: clamp `maxTokens` to 4096 per request; allow at most 100 sampling calls per session (shared across servers).
  The specification requires a human in the loop. Until per-request approval UI exists, that loop consists of the explicit opt-in and these limits.
- v1 scope: text only (image content blocks are skipped); does not return `CreateMessageResultWithTools`
  (augmented tool calls). The specification permits sampling results without tool calls.
- stop_reason mapping: `max_tokens`→`maxTokens`, `stop_sequence`→`stopSequence`, everything else→`endTurn`.

## 7. outputSchema validation and degradation

### 7.1 This behavior affects default builds

Both SDK generations validate a server's actual result against the tool's **advertised** `outputSchema` and **throw an exception** on mismatch. That judgment means the server's self-description is wrong, not that the tool failed to do its work. A server that declares `outputSchema` but returns plain text has a cosmetic bug; failing the entire tool call because of it turns a small bug into a broken turn.

`callMCPTool` therefore classifies these exceptions and **degrades them to text results**. The model can still see the result and the turn survives, while occ emits a debug log and a `tengu_mcp_output_schema_degraded` analytics event.

**The response cache “arms” validation**: the validator is compiled from the cached aggregate `tools/list` result, and only `listTools()` populates that cache. A raw `request({ method: 'tools/list' })` leaves validation inactive. occ's discovery path uses `listTools()`, so this is a **live path**, not merely a safety net. (In addition, `listTools()` handles pagination; the raw request does not.)

Behavioral change: nonconforming servers move from “silently accepted” to “logged and degraded.” **This behavior is era-independent, so it changes default builds.**

### 7.2 Four classifications

`outputSchemaViolation()` in `src/services/mcp/outputSchemaDegradation.ts` returns:

| Value | Meaning |
|----|------|
| `missing_structured_content` | A schema was declared, but no structured content was returned. This is the most common case in the wild |
| `schema_mismatch` | Structured content was returned but did not pass validation |
| `validator_failed` | The validator itself threw an exception |
| `invalid_output_schema` | The declared schema could not be compiled at all; the request was never sent |

The SDK reports all four cases as `ProtocolError` values distinguished only by message text, so text matching is the only available classification mechanism. Classification failures are not silent: an unclassified violation falls through to generic error handling and fails the call, just as it did before the degradation path was wired. This is why tests must drive the real validator with real violations.

### 7.3 `packages/mcp-client` is intentionally not armed

`packages/mcp-client/src/discovery.ts` **deliberately** still uses `request({ method: 'tools/list' })`. It is a parallel implementation that is currently **not wired in** (`src/` never imports its `discoverTools` or `callMcpTool`), and its sibling `execution.ts` has no degradation layer. Arming it would hard-fail the same servers that the host currently degrades. Do not unify the implementations merely for consistency; port the degradation layer first.

## 8. OAuth hardening

This work is **not** behind `feature('MCP_2026')`; it applies unconditionally to every user. These changes fix existing mix-up and cross-tenant credential-confusion problems. Hiding security fixes behind a flag that was disabled by default would prevent users from receiving them.

| Item | Description |
|----|------|
| RFC 9207 `iss` validation | Both the loopback callback and pasted callback URL paths validate `iss` **before** reading `code`/`state`/`error*` (all of which are attacker-controlled in a mix-up attack). The §2.4 decision table delegates to the v2 SDK's `validateAuthorizationResponseIssuer`. Duplicate `iss` values are rejected outright because query parsers disagree about which duplicate wins. Adds the `issuer_mismatch` telemetry reason. The browser-facing 400 page **deliberately does not echo** the received issuer |
| Credentials partitioned by issuer | Slots change from `${serverName}\|${sha256(config)}` to `${baseKey}\|iss:${sha256(issuer)}`. The base key remains the prefix, so all slots for one server can be enumerated without an additional index. Comparison tolerates one trailing slash (matching the SDK's `issuersMatch`); otherwise, two spellings of the same issuer would split into separate slots |
| Migration | Backward-compatible: entries that explicitly name a **different** issuer are reassigned under their own issuer instead of being taken; **unowned** entries (all pre-upgrade installations) are assigned to the first discovered issuer. There is no evidence available for a better assignment, while refusing migration would sign out every existing user. A wrong guess costs one 401—the exact failure these users would already encounter—after which discovery provides the real issuer and the next resolution is exact |
| `application_type: 'native'` | Declared explicitly in DCR registration requests (RFC 8252 §8.3 / SEP-837). occ redirects to loopback, which contradicts OIDC's default of `web`; some servers reject that mismatch outright |

Be aware of the 4096-byte limit for a single macOS keychain item: superseded base entries are **discarded** rather than merged. For the same reason, “clear authentication” now removes all issuer slots for that server.

## 9. Current SDK versions and the v1 retirement sequence

### 9.1 Three packages remain in the tree

`package.json` currently requires all three:

```jsonc
"@modelcontextprotocol/client": "^2.0.0",  // Client; fully adopted
"@modelcontextprotocol/server": "^2.0.0",  // Server; fully adopted
"@modelcontextprotocol/sdk":    "^1.29.0"  // v1; cannot be removed yet; see below
```

### 9.2 Why v1 cannot yet be removed

Distinguish two kinds of remaining dependency: **type imports** (`import type`, erased at build time and required only by `tsc`) and **value imports** (included in the actual artifact).

**Value imports (production code; actual runtime dependency on v1):**

| File | v1 values used |
|------|-----------|
| `src/services/mcp/auth.ts` | `auth`, `refreshAuthorization`, `discoverAuthorizationServerMetadata`, `discoverOAuthServerInfo`, 5 OAuth error classes, `OAuthTokensSchema`, etc. |
| `src/services/mcp/xaa.ts` | `discoverAuthorizationServerMetadata`, `discoverOAuthProtectedResourceMetadata` |
| `src/services/mcp/xaaIdpLogin.ts` | `startAuthorization`, `exchangeAuthorization`, `OpenIdProviderDiscoveryMetadataSchema` |
| `src/utils/mcpWebSocketTransport.ts` | `JSONRPCMessageSchema` |

**Type-only imports (dual-era proof via `implements LegacyTransport`; change these last):**

- `src/services/mcp/InProcessTransport.ts`
- `src/services/mcp/SdkControlTransport.ts`
- `packages/mcp-client/src/transport/InProcessTransport.ts`
- `src/utils/mcpWebSocketTransport.ts` (also has the value import listed above)

The `implements LegacyTransport, ModernTransport` declarations in these classes are **intentional**: they allow the in-process computer-use path to pass the same transport to the v2 `Server`. Removing the v1 half would break v1 consumers that still exist at the other end.

**Tests (dual-era proof):** `src/services/mcp/__tests__/negotiationMatrix.test.ts` (v1 `Server` plus request schemas) and `src/entrypoints/__tests__/mcp.test.ts` (a v1 `Client` calling occ's dual-era server). These tests use real v1 peers to prove that “we can still serve 2025.” They should remain for as long as that claim remains part of the contract.

### 9.3 Retirement sequence

1. **Move OAuth to v2** (`auth.ts` / `xaa.ts` / `xaaIdpLogin.ts`). The v2 package root exports equivalents: `auth`, `startAuthorization`, `exchangeAuthorization`, `refreshAuthorization`, `registerClient`, `discoverAuthorizationServerMetadata`, and others. **One shape changes**: v1's separate subclass for each error (`InvalidGrantError`, `ServerError`, `TemporarilyUnavailableError`, `TooManyRequestsError`) becomes one `OAuthError` discriminated by the `OAuthErrorCode` enum in v2, so the `instanceof` branches must be rewritten. This migration also allows removal of two workarounds: the `& { application_type?: string }` intersection on the `clientMetadata` return type (v1's type omits the field; v2 includes it), and the `unknown` input to `issuerBaselineFromMetadata` (`authorization_response_iss_parameter_supported` is absent from v1's type but accepted by its parser).
2. **Replace the WebSocket transport parser**: change `JSONRPCMessageSchema.parse(x)` to v2's `parseJSONRPCMessage(x)` (signature: `(value: unknown) => JSONRPCMessage`). The error type thrown on parse failure also changes, so review its error handling at the same time.
3. After steps 1 and 2, production code retains only type imports. At that point, `@modelcontextprotocol/sdk` can be **demoted from `dependencies` to `devDependencies`**. The artifact no longer needs it, while `tsc` and the dual-era tests still have access to it. This is a useful intermediate state; complete removal is not required first.
4. Change the dual-era tests and the transports' `implements LegacyTransport` declarations **last**. Removing them abandons the commitment to serve 2025 clients. That must be a separate, deliberate product decision, not a side effect of dependency cleanup.
